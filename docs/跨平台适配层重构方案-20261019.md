# 跨平台适配层重构方案

**项目**：hana-downloader（小花下载器）
**日期**：2026-10-19
**状态**：待评审，未开工
**作者**：主脑（hanako）
**依据**：`docs/踩坑记录.md` 第 45/50/51/52 条、跨平台扫描结果、四轮三平台 CI 实测数据

---

## 0. 摘要

把散在 4 个文件里的 63 处平台相关代码，收进一个 `engine/platform/` 层。

**规模**：13 个文件 5259 行的引擎，平台代码集中在 `aria2.js`(25)、`dlcore.js`(21)、`proxy-control.js`(13)、`server.js`(4)，其余 9 个文件零处。

**工期**：分三档，最小可用 4-5 天（现实估算），功能对齐 8-12 天，完整移植 16-24 天。

**收益的性质**：不是"少写 if"，是**让错误从结构上不可能发生**。今天挖出的那个 `spawn(cmd)` 没给 `detached` 而 `kill(-pid)` 却在别处依赖它，隔了 160 行、两个函数、其中一处做了非 Windows 分支另一处忘了——这种缺陷是结构允许出来的，不是谁粗心。

**代价**：抽象层自身会腐化。没有测试守着的抽象层，两年后比现在更糟。所以第一步不是"建 layer"，是"建 layer + 建测试"。

---

## 1. 判据：这活值不值得干

三个前提，缺一个结论就翻转。

### 1.1 三平台是真需求，不是"万一"

如果只是"怕以后有人在 mac 上装"，不划算。为一个假想需求动 5000 行核心，风险大于收益。

如果有真实用户或确定要往那个方向交付，划算。

**当前判断**：仓库已公开、已有 CI，方向是"别人也能用"。倾向划算，但这一条需要 John 确认。

### 1.2 别把 proxy-control 和 winget 算进收益

这两块即使重构了也是**裁剪**而非移植：

- `proxy-control.js` 393 行，逻辑是「读注册表 → 扫 `.exe` → `tasklist` 查进程 → `taskkill` 杀」，mac/linux 上一项都不成立
- `winget` 82 处，是 Windows 专有的包管理器

这两块不产生重构收益，别让它们把账算漂亮。

**真算收益的，是那十组通用接口**：找可执行文件、起进程、杀进程树、读目录、路径规范化。这些每个平台都需要，抽象一次吃三份。

### 1.3 必须分步，不能一次动完

`AGENTS.md` §2.1 的教训：一天四轮修复，至少两轮引入新问题，都是「改一处验一处，没回头验旧功能」。

5000 行核心一次动完，21 个套件全绿的基线会被打碎，且很难知道碎在哪一步。

## 3. 目标架构

### 3.1 目录结构

```
engine/platform/
  index.mjs      按 process.platform 选实现，导出统一接口 + capabilities
  win32.mjs
  darwin.mjs
  linux.mjs
```

业务代码只 `import { platform } from "./platform/index.mjs"`，**不许再出现 `process.platform === "win32"`**（唯一例外：`platform/` 目录内部）。

### 3.2 十组接口

```js
export const platform = {
  name,                    // "win32" | "darwin" | "linux"

  // ① 查找可执行文件
  which(cmd),              // → string | ""

  // ② 可执行文件名
  exe(name),               // "aria2c" → "aria2c.exe" | "aria2c"

  // ③ 起子进程的默认选项  ★
  spawnOpts(extra),        // win: {windowsHide:true}  posix: {detached:true}

  // ④ 杀进程树  ★
  killTree(pid),           // taskkill /T /F  |  process.kill(-pid, SIGTERM)

  // ⑤ 进程是否在跑（按名字）
  isRunning(name),         // tasklist  |  pgrep

  // ⑥ 打开文件所在位置
  reveal(path, mode),      // explorer /select,  |  open -R  |  xdg-open

  // ⑦ 读系统代理
  readSystemProxy(),       // reg query  |  scutil --proxy  |  gsettings/env

  // ⑧ 用户目录 / 临时目录
  homeDir(), tempDir(),

  // ⑨ 能力表（不是平台判断，是"这个平台有没有这个功能"）
  capabilities,            // { pkgManager, proxyControl, reveal }

  // ⑩ 路径规范化
  normalizePath(p),        // 大小写、分隔符、符号链接
};
```

### 3.3 三条设计原则

**原则一：`spawnOpts` 和 `killTree` 必须在同一个文件里，中间不许隔别的代码。**

这是本方案最重要的一条，来自今天的真实缺陷：

```js
// dlcore.js:550 —— 起进程，没给 detached
child = spawn(cmdBin, fullArgs, { cwd, stdio, windowsHide: true, env });

// dlcore.js:716 —— 杀进程树，依赖 detached（隔了 160 行、另一个函数）
process.kill(-t.child.pid, "SIGTERM");
```

`kill(-pid)` 要求子进程是进程组组长，而 `detached: true` 才建立独立进程组。**两处分离，必然有一处被忘掉。**

收进 platform 层后，起进程和杀进程树在同一个命名空间里，"忘掉一个"这件事在物理上不存在。

**原则二：上层不许判断平台。**

业务代码只问 `platform.capabilities.pkgManager` 有没有值，不问"这是不是 mac"。

这和 `backends/contract.js` 的 `capabilities()` 是同一个模式。项目里已经有这个先例，等于把同一套设计语言用第二次。

**原则三：「不支持」是显式状态，不是运行时报错。**

mac 上没有 winget，不是"调用失败退出码 -2"，而是 `capabilities.pkgManager === null`，UI 直接不显示这个选项。

**能力探测必须建立在真实往返上。** 这是项目铁律（`available:true` 必须来自真实 RPC 握手），平台层同理：`brew` 存不存在要真调一次 `brew --version`，不能靠"路径上有这个文件"推断。

## 4. 迁移路线

### 第一步：建层 + 建测试（1.5-2 天，独立可验）

**只加文件，不改任何现有代码。** 现有 21 个套件必须保持全绿。

- 三平台实现 + 十组接口，约 300-350 行
- 单测：接口接受 `{ platform: "win32" }` 这样的参数注入，**一套断言同时验三条分支**
- 这一步做完，能立刻看到接口是否设计得够用

**验收**：`platform/` 单测全绿；`run-tests.mjs` 21/21 未变；`git diff` 里没有任何现有文件被修改。

### 第二步：逐文件收编（2-3 天）

按风险从低到高，**一个文件一批，每批跑全量**：

| 批次 | 文件 | 处数 | 说明 |
|---|---|---|---|
| 1 | `server.js` | 4 | 最安全，含那个会崩的 `explorer.exe` |
| 2 | `dlcore.js` | 21 | 含 `spawnOpts`/`killTree` 配对的关键修复 |
| 3 | `backends/aria2.js` | 25 | 大部分在候选路径表里，机械但量大 |

**每批的验收**：`run-tests.mjs` 21/21 + 三平台 CI 绿。

### 第三步：功能性差异（独立决策）

- `proxy-control`：裁剪（0.5 天）或真做（3-5 天）
- `winget`：非 Windows 不注册（0.5 天）
- `pip`/`uv` 的 PEP 668：探测 `externally-managed` 给出明确提示（1 天）

**建议裁剪**：先把「能下载」在三个平台跑通，辅助功能等有人真在 mac 上提需求再说。

## 5. 明确不做的事

| 不做 | 理由 |
|---|---|
| 把 `proxy-control` 照搬到 mac | 整个模块的形态是 Windows 的（读注册表、扫 `.exe`、tasklist），mac 用户的梯子习惯（ClashX/mihomo/sing-box）差很远，搬过去也不对味 |
| 把 winget 抽象成 brew/apt 插件 | 三种包管理器的输出格式、退出码语义、进度表达全不同，是一块独立子系统。先保证下载 |
| 为测试改产品行为 | 唯一例外是 `resolveAria2Bin` 加可选候选表参数——那个参数本身有实际价值（可配置搜索路径），且默认行为完全不变 |

## 7. 风险与对策

### 7.1 宿主沙箱在 mac 上的行为（最高风险，完全未知）

宿主在 mac 上用 `sandbox-exec`、linux 上用 `bubblewrap`。对文件写入的限制可能和 Windows 的 `hana-win-sandbox.exe` 完全不同。

**如果 `sandbox-exec` 不允许引擎往 `~/Downloads` 写，整条下载链路要重新设计落盘位置。**

这一条可能把估算整个推翻，且只能等真机验证。

**对策**：最小可用档位的最后一步就是三平台真机验证，先撞这个墙，再决定要不要投入后面几档。

### 7.2 `detached: true` 的副作用

一旦给命令型子进程加上 `detached`，它有了自己的进程组和会话。会不会导致它脱离引擎生命周期、变成真正的孤儿（引擎崩了但 uv 还在跑）？

**这和"能杀掉它"是同一枚硬币的两面。**

**对策**：第二步收编 `dlcore.js` 时，专门写一条用例验证「引擎异常退出后，命令型子进程是否被清理」，不能只验"取消能杀掉"。

### 7.3 抽象层自身腐化

接口设计不足的话，半年后加新特性还要往里塞参数，慢慢又变成杂物间。

**对策**：平台层必须有测试守着，每次加接口先写断言。没有测试的抽象层，两年后比现在更糟。

### 7.4 CI 的盲区

- `macos-13` 排不到 → Intel Mac 分支零验证
- CI 只验 engine 纯逻辑，验不了宿主启动和 UI

**对策**：明确区分「CI 绿了」和「能在 mac 上跑起来」，不要混为一谈。
