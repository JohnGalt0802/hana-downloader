# 排查：下载卡片「切会话回来变满宽 + 变高」

> 日期：2026-10-13 深夜
> 宿主：HanaAgent 1.1.0-beta（win32-x64）
> 用户报告：聊天流里的下载卡片，切换会话再回来后「又变成满宽、高度也涨开（像展开详情的高度）」。
> 用户直觉：卡片与宿主的通讯问题。
> 证据来源：宿主 renderer bundle（`ChatTranscript-CLxbpBJm.js` / `ChatTranscript-RJ9dRel7.css`）、
> 本仓 `ui/card.js`、`ui/manager.js`、`docs/踩坑记录.md`。

---

## 一、结论（一句话）

**用户直觉对了一半：这是「卡片→宿主的尺寸上报在 iframe 重建后没有生效」导致的，不是卡片渲染坏了。**
宿主在未收到上报时用的是**默认尺寸（满宽 100% + 按 `aspectRatio` 推出的高度）**，而下载卡
`details.card` 声明的是 `aspectRatio:"8:1"`，所以宽度一满，高度就跟着变成「宽/8」——看起来就是
「满宽 + 高得像展开态」。**宽度和高度是同一条上报通道的两个字段，所以『两个尺寸一起失守』是同一个 bug。**

---

## 二、宿主侧事实（读码所得）

### 2.1 切会话 = iframe 卸载重建，不是隐藏复用
下载卡在聊天流里由 `plugin_card` 块渲染（工具返回值 `details.card` → `plugin_card` → 组件 `VQ`）。
聊天按会话渲染，切换会话时当前会话的整棵聊天树卸载，切回时重建 → **iframe 重新加载、卡片脚本重跑**。
宿主另有 `data-card-host-park` / `moveBefore` 的「保留+移位」机制，但**只服务卡片中心/Chalkboard，不服务聊天流卡**。

### 2.2 卡片宽高都由「卡片自己上报」，未上报时用默认值
`VQ`（`ChatTranscript-CLxbpBJm.js`）：
```
c.jsxs(eg,{ ... maxWidthPx:T.width ?? void 0, children:
  c.jsx("div",{ className:`${En.frame}${B?"":` ${En.frameFlush}`}`, style:X, children:
    c.jsx("iframe",{ className:En.iframe, ... }) }) })
```
- 宽度：`maxWidthPx = T.width`（来自卡片上报）。T.width 未上报 → 无 maxWidth → 卡壳 `_card_ed568 { width:100% }` **满列宽**。
- 高度：`X = T.height!=null ? {height:T.height, maxHeight:z} : (aspectRatio ? {aspectRatio:G, height:"auto"} : {})`。
  `G = WQ(e.aspectRatio)`，`aspectRatio:"8:1"` → `G=8`。
- 卡壳默认高度（无上报时）：`_frame_12cf1 { height:480px; max-height:720px }`。

**⇒ 未上报时的表现 = 满宽 + 高（480px 或按 8:1 推出）——正是用户看到的样子。**

### 2.3 上报通道：`hana.ui.resize` 在聊天流是接得住的（纠正旧判断）
卡片发 `window.parent.postMessage({protocol,kind:"event",type:"ui.resize",payload:{width,height}})`，
renderer 由 `xz()` 解析 → `{kind:"resize", size}` → `Wz` 内 `He(size)` → `Oz(slot, size, prev, innerHeight)`：
```
function Oz(e,t,n,r){ if(e==="card"){ const i=t.width!==void 0?Math.max(Iz,t.width):n.width,
  a=t.height!==void 0?Math.max(wz,t.height):n.height; return {width:i,height:a} } ... }
const Iz=50, wz=30, QA=100, ...
```
即 **card slot 下上报的 width/height 都被采纳**（下限 50 / 30）。所以宽度是**可上报可控**的，
不是「宿主锁死满宽」。`preferredWidthPx`（`details.card` 里那个 400）在这条路径上**不参与**卡壳宽度。

### 2.4 尺寸状态随重建归零
重建后组件内尺寸 state 归默认（无 width/height），宿主先按默认渲染，等卡片重报才收窄。
**这与「切回后先满宽、再（若上报到达）收成 400px」一致。**

## 三、App 侧事实（读码所得）——上报的「窗口」很窄

`ui/card.js`：
- 上报函数 `reportSize(force)`：`if(!force && h===lastReportedH) return;` —— **去重只看高度，未变就不发**。
- 强制补报只有几处且一次性的：
  - `bootSettle`：模块加载时首帧 1 次 + 每 1.5s 最多 6 次（≈9s）；
  - 终态切换 `[0,1000,2500]ms` 各一次（`terminalReported` 守卫，**每个终态只跑一次**）；
  - `window resize` 事件（**仅 `!adopted()` 时**才 force）。
- `adopted()`：`Math.abs(window.innerWidth - 400) <= 2` —— **只验宽度、不验上报是否真被采纳**。
  宽≈400 时立刻收兵，哪怕这次上报被丢。

**⇒ 死锁**：卡片记的是「自己量到的高度」，不是「宿主实际施加的尺寸」。一旦「强制补报窗口」关闭、
而内容高度又稳定（终态卡正是如此），后续 `reportSize()` 全是 no-op。**此时若宿主把尺寸重置为默认
（重建导致），卡片没有任何机制去纠正。**

`ui/manager.js` 更薄：无 `bootSettle`、无终态补报、无 `ResizeObserver`，只有 init 一次 + resize 监听。

（已排除：开发目录与运行副本 `ui/card.js` 等 5 个文件 SHA256 完全一致，不是「改了没同步」。）

## 四、链条合成

```
切会话 → 宿主卸载并重建卡片 iframe（脚本重跑）
        → 宿主尺寸 state 归默认：满宽 + 8:1 高度
        → 期望：卡片重跑后重新上报 400×H，宿主收窄
        → 实际：卡在某处没生效（见下），宿主一直用默认
        → 表现：满宽 + 变高（两者同源）
```

## 五、还没钉死的一环（需一次运行时实测）

「重建后上报为什么没生效」有两条候选，静态读码无法排他：

- **候选 A（宿主/时序）**：重建瞬间的首次上报落在宿主 `message` 监听/尺寸应用路径就绪之前，被丢弃；
  而 App 侧窗口（≈9s 或 adopted 提前收兵）过后不再重报 → 停错。
- **候选 B（App）**：`adopted()` 在重建后窗口宽恰好落入 400±2 时误判「已采纳」，提前收兵，
  把唯一能纠错的 9s 窗口压缩掉。

**判定手段（一次即可钉死）**：在 `ui/card.js` 的 `reportSize` 内加一段临时诊断（`hana.track("sizerpt",{force,h,iw:innerWidth,adopted})`），
复现「切会话回来」，读诊断日志：
- 若**切回后 30s 内上报次数 ≈ 0** → 候选 B（App 侧收兵太早）；
- 若**有上报但 innerWidth 始终≈满宽** → 候选 A（上报丢失/通道时序）。

## 六、修复方向（备选，未实施）

1. **re-show 强制补报**：监听 `document.visibilitychange` / `pageshow` / 宿主 surface 事件，
   re-show 或重新绑定时强制补报几轮（照 `terminal` 一次性补报的写法）。这是**最直接的兜底**，不依赖死因。
2. **去重键改为「感知是否被采纳」**：不只比 `lastReportedH`，同时比「宿主回灌的 innerWidth 是否符合期望」；
   不一致就重报（打破 no-op 死锁）。
3. **修 `adopted()` 误判**：宽度已采纳不代表高度信道上报成功；把高度也纳入判定，或干脆不提前收兵。
4. **manager 卡补齐 `bootSettle`/`ResizeObserver`**，与 card.js 对齐。
5. **上报宽度也参与去重/重报**（现在宽度是常量、不参与变化判断）。

> 优先级建议：1 + 2 一起做（治本 + 兜底），3 顺带，4 同批对齐。
