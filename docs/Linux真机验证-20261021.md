## 二、宿主怎么起来的（含两个坑）

用的是 `server-1.1.35-beta-linux-x64.tar.gz`（230 MB，无 GUI 的 server 版）。

**坑 1：`v0.450.0` 的 server 包是坏的。** 解开后 `shared/artifact-core/` 整目录缺失，
`./hana` 直接 `MODULE_NOT_FOUND: '../shared/artifact-core/activation.cjs'`。
换成同 tag 下 `train-beta-40` 的 `server-1.1.35-beta-linux-x64.tar.gz` 才正常（`shared/artifact-core/` 有 10 个文件）。
**这条记在踩坑记录 #60。**

**坑 2：官方包自带的 node 缺 `libatomic.so.1`。** 报错是
`error while loading shared libraries: libatomic.so.1`，`apt-get install -y libatomic1` 解决。
WSL 最小 rootfs 没这个库，官方 deb 包大概率会带依赖声明，tar 包不会。

启动方式：

```bash
export HANA_HOME=/root/hanahome135
cd /root/hana && ./hana-server          # 端口由它自己选，写在 $HANA_HOME/server-info.json
```

就绪标志：日志出现 `[server] ready: port=34877`，且 `server-info.json` 里有 `token`。
之后所有 API 都要 `Authorization: Bearer <token>`。

## 三、装 App：走真实管线，不手放目录

宿主的规则是「只认安装记录」——目录放在 `apps/` 里但没批准记录，`state` 会停在 `unregistered`，
一行代码都不跑。所以照抄用户点「批准」时的那条路：

```
POST /api/extensions/install  {"source":{"type":"unregistered","id":"hana-downloader"}}
  → {"status":"awaiting_confirmation","staged":{"stagedId":"stg_..."}}
POST /api/extensions/staged/<stagedId>/confirm
  → {"status":"installed","ref":"app:hana-downloader",...}
```

`GET /api/apps` 随后给出 `state: loaded`，引擎子进程随之起来：

```
/root/hana/node /root/hanahome135/apps/hana-downloader/engine/server.js /root/hanahome135/app-data/hana-downloader
```

**顺带一个平台层真机确认**：引擎的 `GET /settings` 回

```json
{"platform":{"name":"linux","proxyControl":false,"pkgManager":"apt","reveal":true}}
```

`pkgManager: "apt"` 是真调 `apt --version` 得到的，`proxyControl: false` 是裁剪生效。

## 四、★ 方案书里的「最高风险」问错了对象

方案书 §7.1 写的是：

> 宿主在 mac 上用 `sandbox-exec`、linux 上用 `bubblewrap`。对文件写入的限制可能和 Windows 的
> `hana-win-sandbox.exe` 完全不同。**如果 `sandbox-exec` 不允许引擎往 `~/Downloads` 写，
> 整条下载链路要重新设计落盘位置。**

实测下来，这句话的前提不成立：**下载器引擎跑在 `local-machine` 模式，这个模式根本不过 bwrap。**

证据链三条：

**① 读宿主源码**，bwrap 只在那一条路上：

```js
// 宿主 bundle/index.js（1.1.35-beta）
function $dn(t, { getExternalReadPaths: e, ... }) {
  ... n.confine(["/bin/bash", d], { backend: "bwrap", policy: t, ... })
}
```

这条是**agent 的工具执行**（跑 bash 命令）。而 `local-machine` 是另一条：

> 受管进程以当前 OS 用户权限访问和修改本机可访问文件、运行本机命令；这可能包括其他应用的数据
> 和磁盘上的凭据文件，**不提供文件系统或网络隔离**。
> —— `APPS.md`「托管 `local-machine`」一节

**② 看进程现场**，引擎进程没有任何 namespace 隔离：

```
engine pid 1835:  /root/hana/node .../engine/server.js ...
mnt ns   = mnt:[4026532211]     ← 与 app-host、与 init 完全同一个
NoNewPrivs = 0
Seccomp    = 0
```

如果过了 bwrap，`/proc/<pid>/ns/mnt` 一定与父进程不同（bwrap 至少 unshare mnt）。同一就等于没隔离。

**③ 实跑落盘**，往 HANA_HOME 之外写，直接成功：

```
POST /download {"url":"https://example.com","saveDir":"/root/Downloads"}
→ state: done, path: /root/Downloads/probe.html, 577 字节
```

非 root 用户（uid 1000）跑同样一条，写自家 `~/Downloads` 也成功。

**所以正确的表述是**：Linux 上 bwrap 管的是 **agent 的 shell 工具**，不是 `local-machine` 的受管程序。
下载器落盘不受 bwrap 限制。方案书 §7.1 需要按这一条修订——它担心的事发生在另一条通道上。

**这一条同时说明另一件事**：`local-machine` 没有文件系统隔离，意味着「引擎能写哪」完全由
OS 用户权限决定。第一次用非 root 用户跑时确实撞了一次 `EACCES`（`/home/dluser/Downloads` 属主是 root），
`chown` 之后正常。这不是产品 bug，是现场造错了。

## 五、进程树：能杀、能收，但收的口径原来是错的

### 5.1 取消能杀掉整棵树（本来就对，这次有了真证据）

起 230 MB 的本地 git 仓库做克隆，取消后：

```
取消前：git clone（2259）→ sh（2260）→ git-upload-pack（2261）→ pack-objects（2263）→ index-pack（2264）
POST /cancel → {"ok":true,...}
取消后：pgrep 找不到任何 git / remote-https / index-pack
```

五个进程一次清空，`kill(-pid)` 在真 Linux 上成立。

### 5.2 ★ 孤儿收尾原来在空转（这次修掉）

审查 A 指出的错配：

```
_reapOrphanCommand:  pidAlive(pid)              ← 探的是「组长」
                     killTree(pid) → kill(-pid)  ← 杀的是「进程组」
```

`tests/tools/orphan-posix-mechanism.mjs` 把这个现场造出来并数了出来：

```
ok   组长已退出（pidAlive 为 false）            pid=6749
ok   组长死后组员还活着（心跳仍在增长）          14 -> 20
ok   ★ 但进程树仍可探活（treeAlive 为 true）    -6749
ok   treeNames 能问到组员（组长已死也问得到）   ["node"]
```

同一时刻、同一个 pid：**`pidAlive` 说死，`treeAlive` 说活**。旧写法用前者探、用后者杀，
在最需要它的时候必然直接 return。

**修法**：平台层加两个接口，让探活与杀指向同一个对象。

| 接口 | posix | win32 |
|---|---|---|
| `treeAlive(pid)` | `kill(-pid, 0)` | 退化为 `pidAlive` |
| `treeNames(pid)` | `ps -A -o pgid=,comm=` 按 pgid 筛 | 退化为 `processNameOf` |

`_reapOrphanCommand` 改用这两个，并顺手修了第二个隐患：核名从「只看组长」改成「看整棵树」——
真正的写入者是孙子进程（`git-upload-pack` / `index-pack` / uv 拉起的 python），
组长如果是个 `sh` 包装，只看组长名字会核不上。

**为什么 win32 退化是正确的、不是偷懒**：Windows 没有进程组，`killTree` 走 `taskkill /T` 的
**进程树关系**；父进程一死，这层关系就断了，`taskkill /T <pid>` 本来也没东西可杀。
posix 上则相反：组还在，`kill(-pid)` 有东西可杀。两端不同构，所以分别断言（见 `unit-orphan-reap.mjs`）。

**还有一个前提必须验**：组长已死、组还活着时，`kill(-pid)` 会不会打到别人的组？
这取决于「进程组存活期间 pgid 是否会被复用」。`tests/tools/pid-reuse-vs-group.mjs` 直接测：

```
组长已退出 → 进程组仍存在 → 起 300 个短命进程（船到 300 个不同 pid，最大 4350）
→ oldPid=4012 一次都没被复用 → 组在此期间始终活着 → 组员仍在跑
```

进程组存活期间 pgid 被内核占住不可复用，`kill(-pid)` 仍然只指向我们当初建的那个组。**可以安全清组**。

**⚠️ 这条推理有个边界，复核后来指出了（必须读）：** 上面证明的是「组还在时，kill(-pid) 安全」。
但**误杀恰恰发生在「组已经消失、pid 被复用」之后**——那时新组是完全陌生的，这条前提管不着。
也就是说，「pgid 不可复用」不能当作核名可以放宽的理由。两件事被当成一件了。
这条修正直接导致了下面 §5.4。

### 5.4 「核名」这条路本身就不可靠，改用启动指纹（2026-10-21 复核后重修）

先说这次我自己引入的一个缺陷——它比原来那个还危险，值得完整记下来。

第一次修的时候，我把 `"sh" / "bash"` 加进了期望镜像名，理由是「组长可能是个 sh 包装」。
复核把两半都拆了：

**动机不成立**。四条链路全是直接 spawn（`git` / `node` / `winget` / `python|uv`），
全仓 `shell: true` 零处。真实树里 sh 只是中间层（`git → sh → git-upload-pack`），不是组长；
而 `sh -c "单个命令"` 会被 **exec 掉**，连作为独立成员都不存在。

**风险已经复现**。shell 恰恰是桌面上最常见的**组长**：终端里的每条作业、每个 `setsid`
启动的服务、每个 login shell，pgid 都等于自己的 pid。复核实测：

```
无关 bash 组长 pid = 24214
treeNames = ["bash","sleep"]
_reapOrphanCommand(24214, "pnpm-install") = true
0.7s 后 bash 组长还活着?  false      ← 整个组被打掉
```

安全阀从「树里必须有真正干活的镜像名」降级成了「树里有个 shell」。配上 pid 复用就是一次真实的误杀（复核用 `ns_last_pid` 精确复现了）。

**所以做了两件事：**

1. **shell 全部移出期望集合**，连同 `dash` / `zsh` 也不列。名字硬编码这条路两头都不稳，宁漏勿错。
2. **加启动指纹 `processStartOf(pid)`**，把「核名」从唯一依据降为旁证：
   | 平台 | 读法 | 拿不到时 |
   |---|---|---|
   | linux | `/proc/<pid>/stat` 第 22 字段（内核 jiffies） | 不拦 |
   | darwin | `ps -o lstart=` | 不拦 |
   | win32 | 有意返回 `""` | 不拦 |

   `_persist()` 落盘 `childStart`，`restore()` 时传给收尾函数；两边都有值且对不上 → 认定 pid 被复用，直接放弃。
   这是目前**唯一不靠「内核会替我占住号」的做法**，也是 macOS 那个未验证前提的替代方案。

**指纹的精度局限（实测写清，不要以为它什么都能挡）**：jiffies 单位常见 100Hz（10ms），
同一轮 fork 出来的进程会落在同一个 tick、指纹相同。它能挡住「几分钟前那个 pid 被新进程顶替」，
挡不住「10ms 内恰好撞上」。那个窗口只能靠核名堆着，两层都不完美，但比原来只有一层强。

**win32 返回空指纹是有意的**（复核问过，这条写实）：Windows 没有进程组，`killTree` 走
`taskkill /T` 的进程树关系，父进程一死树关系就断，不存在 posix 那种「组长已死、组员还在」的窗口；
而拿一次启动时间的代价不是零（wmic 在新 Windows 已移除，本机实测不存在；`Get-CimInstance` 一次 121 ms，
而 `_persist()` 是高频路径）。将来要补，得先找到不靠外部进程的做法。

### 5.5 第二个结构漏洞：non-leader 分支的谎报

复核还指出：`treeAlive` 对「pid 活着但 pgid≠pid」返回 true，但 `_reapOrphanCommand`
当时唯一的动作是 `killTree(n)` → `kill(-n)`，对非组长 pid 是 **ESRCH**。函数返回 `true` 却什么也没杀。

```
leaderPid = 23488  childPid = 23496
23496   23488   23488 node          ← 子进程不是组长
treeAlive(child) = true
_reapOrphanCommand(child, "pnpm-install") 返回 = true
1.2s 后 pidAlive(child) = true      ← 根本没杀，函数却说收掉了
```

今天四条链路都走 `platform.spawnOpts`（childPid 恒为组长），这个分支摸不到。
但「探与杀指向同一对象」这个不变量没兼现——而这次改动的全部理由就是它。

**补了 `treeKill(pid)`**，三平台分别实现：
- posix：pid 活着且 pgid≠pid → **只杀自己**（SIGTERM → 5 秒后 SIGKILL）；否则交给 `killTree` 杀整组
- win32：直接转交 `killTree`（树就是「这个进程 + 子树」，本就没有歧义）

`_reapOrphanCommand` 从 `killTree` 改用 `treeKill`。探、核、杀三步现在指向同一个对象。

### 5.6 第三个漏洞：`treeKill` 的升级定时器会打死抢号的无关进程

这是补 `treeKill` 时**新引入**的，复核用强制抢号实际打死了进程才暴露。

`killTree` 的组版本要等到「一个同号的新进程组出现」才会误伤；而单 pid 版本只要
「同一个号被复用」就夠 —— 门槛低一个量级。原来的升级探活是：

```js
() => { process.kill(n, 0); return true; }   // 号被抢了照样返回 true
```

目标在 SIGTERM 后 300ms 就死了，那个号可能在 5 秒窗口内被别的进程拿走，
`kill(n,0)` 就会成功，定时器便对**无关进程**发 SIGKILL：

```
目标（非组长）pid = 20990  现在活着? true
treeKill 返回 = true  300ms 后目标还活着? false     ← 已经死了
抢号结果：stranger.pid = 20990  ★ 抢到了
★ 5.6 秒后 stranger 还活着? false                   ← 被升级定时器打死了
```

**修法**：发 SIGTERM 前记一次指纹，升级探活改成比对指纹。判据抽成
`escalationAllowed(pid, startBefore)` 三个情形分别可验（进程已死→不升级；
没有记录指纹→保守升级；指纹变了→绝不升级）。

为什么必须抽成函数：自然条件下 pid 复用到同一个号要 `pid_max` 次 fork
（本机 4194304），端到端根本造不出来。难触发但后果重的分支，只有抽出来才能单独测。

### 5.7 四次修完之后的回归验证：变异测试

这套测试被推翻两次，第三次才算真的能看：

| 代 | 问题 | 被什么抓到 |
|---|---|---|
| 第一代 | 6 条源码正则断言是自证（切片失配时 body 为空串、无条件通过） | 复核 M0-M3 |
| 第二代 | 场景 B 写成 either-or、指纹接线无断言 | 复核 M4/M6/M7 |
| 第三代 | 升级探活藏在闭包里，只能靠强制抢号验证 | 自己的变异测试 M7 |

**最终 8 个变异全部被抓到**（`tests/tools/mutation-check.sh`，基线 81 项）：

```
M1 treeKill → killTree                 5 failed
M2 把 sh/bash 加回期望集合              3 failed
M3 treeAlive → pidAlive                 3 failed
M4 非组长分支改成永远不杀                 5 failed
M5 restore 不传 childStart              1 failed
M6 _persist 永远写 null                  1 failed
M7 升级探活退回 process.kill(n,0)        1 failed
M8 escalationAllowed 不再比对指纹         1 failed
还原                                     81 passed
```

**接线断言当场抓到两个真 bug**（这两个都只有端到端能发现）：
1. 指纹挂在 `task._childStart`，却从 `t.child._childStart` 读回来 —— 落盘永远是 null。
2. `_resetTaskManager()` 只清 `_instance`、不清 `globalThis.__dlTaskMgr`，
   后续仍拿到旧实例，带着错误的 `dataDir`（复核写探针时被绔了两次，我写接线断言时又绔了一次）。

**一个容易错过的分层**：M7 一开始没被抓到，因为我的单元测直接测 `escalationAllowed` 本身，
而 M7 变异的是「`treeKill` 还有没有调用它」。补了一条静态断言才抓到。
这里的分层值得记住：

| 层 | 编号 | 手段 |
|---|---|---|
| 逻辑对不对 | `escalationAllowed` 三种情形 | 行为断言 |
| 有没有人在用它 | `treeKill` 必须调用它 | 静态断言 |

静态断言不是一概不可用，“源码正则都是装饰”那个结论是有适用范围的 ——
判断标准是「这个断言能不能在缺陷回来时真的失败」。

**加静态断言时踩的一个小坑**：想顺手禁掉 `process.kill(n, 0)` 这个字符串，
但 `treeKill` 的注释里就写着这个反例（“不能只看 process.kill(n,0)”），纯文本断言
分不开注释与代码，造成一次假红。删掉那条，只留“必须复用 escalationAllowed”。

## 七、平台层 13 组接口的真机往返

`tests/tools/platform-linux-probe.mjs`，31 项全过。挑几个「只有真机才能验」的：
