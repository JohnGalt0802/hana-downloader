## 问题 5：有没有“会话切换 / 页面切换 / 时间线条目重新渲染”会清掉卡片尺寸状态的路径？

**结论：有两条会让“尺寸状态归零/重置”的路径，但都不是“永久清除”，而是“重置为 默认/恢复值”：**
1. **会话切换 = 组件卸载重建**：高度 state `A` 随 `aQ` 卸载归 `null`，宽度无 state（恒 100%）。重建后高度回落到 `ds = min(null ?? Wt ?? 48, 上限)`——若 localStorage 里 (entityId, 当前宽度) 有上次高度则恢复，否则 `48px` 默认，再由卡片重报撑开。这是“切回后先 48px 再涨开”的直接来源。
2. **park/claim（Chalkboard 卡，非聊天流）**：iframe 被移入 `data-card-host-park` 隐藏容器、再 claim 回（`moveBefore`，不重建、不触发 load），此时尺寸由卡壳 CSS（height:auto / 100%、width:100%）与卡片自身决定，组件 state 不丢；但若 claim 进的是不同宽度容器，宽随容器、高度由卡片 content 重新决定。

**未找到任何“主动删除 localStorage 尺寸缓存”的会话/页面切换路径**；缓存只写不删（除内存/LRU 上限 `og`、`eQ=256`，属容量淘汰不是语义清除）。

证据：

- `A` state 随组件卸载归 null：`[A,k]=p.useState(null)`（`ChatTranscript-CLxbpBJm.js:1655`）；重建后 `ds` 公式使用该 null 回落（`ds=...Math.min(A??Wt??jI,...)`）。
- 高度恢复 `Wt`（localStorage，按实体+宽度）：`Wt=l==="chat"&&A==null&&st&&E?YX(st,E):null`（同上 Q2）。
- park 容器与 claim（无 load、无 state 清除）：`ChatTranscript-CLxbpBJm.js:15` 的 `zN`/`yS`/`qN`，使用 `moveBefore`。
- 缓存容量淘汰而非语义清除：`Jp`/`zX` 的 LRU：`ChatTranscript-CLxbpBJm.js:1654` 约偏移 136019/136488（`Pr`/`localStorage` 超过 `og`/`eQ=256` 时淘汰最旧）。
- 卡壳 CSS 决定显示尺寸（无独立“清除”逻辑）：`ChatTranscript-RJ9dRel7.css` 的 `._interactiveArtifactViewport_*`（`width:100%`）、`._interactiveArtifactFrame_*[data-variant=chat]`（`height:auto`）。

未确认项：
- 未确认是否存在“会话列表/UI Surface 切换导致 `aQ` 仅隐藏不卸载”的代码路径（从 `aQ` 实现看，chat 变体高度由 state 驱动、`A` 默认 null，重建语义明确；隐藏复用路径未在聊天流中找到）。
- 未确认 `chatHeightCapPx` 是否非 null（决定 `nr` 上限，影响“高度是否会被钳制而不涨开”）。

## 附：与用户怀疑（撑满宽/涨开/交互失效三合一）的对应
- **撑满宽度**：不是缺陷，是卡壳 CSS `width:100%`（聊天列满宽）的固有设计；`hana.card-resize` 上报的 `width` 仅用于 localStorage 高度分桶缓存，不回写卡壳宽度。
- **涨开**：切回会话重建 → 高度 state `A` 归 null → 先 `48px` 默认（`jI`）或由 localStorage 恢复，再等卡片重报撑开（`ResizeObserver`/`hana.card-ping`）。若 App 卡片在重建后首次重报时机过晚或宽度分桶不匹配（恢复值取不到），会先塌成 48px 再跳涨。
- **交互失效**：重建 = 全新 iframe 加载，卡片内运行时状态与监听器全部重来；宿主虽在 `load` 时发 `hana.card-ping` 与 sizing 模式，但若卡片脚本在 load 之前就尝试通讯（时序竞态），或 App 侧依赖 `hana.ui.resize`（SDK 通道，聊天流 `aQ` 侧未发现接收方）而非顶层 `hana.card-resize`，则可能出现“尺寸/交互通道对不上”。
