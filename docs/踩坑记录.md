# hana-downloader-app 踩坑记录

本文件记录 v2 App 迁移过程中踩到并修复的坑。每条按「现象 → 排查 → 根因 → 解法」写，
后三条只写宿主侧通用结论，与下载器本身无关，做其它 v2 App 也会遇到。

宿主版本：HanaAgent 0.946.2（win32-x64）起写，现行 0.1013.2（2026-09-21 更新）

---

## 1. `/download/*` 是宿主的保留前缀

**现象**：引擎自监听端口后，请求 `/download/status`、`/download/list` 一律 404，
像路径被吃掉了一段。

**排查**：把路径换成 `/wait`、`/list` 这类不带 `/download/` 前缀的写法，立刻正常。

**根因**：宿主的 App 运行时路由把 `download` 当保留段处理，落在 `/download/` 下的
路径在转发前就被截断或改写了。

**解法**：引擎对外暴露的路径避开 `/download/*` 前缀。本项目的实际接口是：

```
GET  /ping
POST /download      ← 这个路径本身没问题，是它下面的子路径有问题
POST /command
POST /wait
GET  /wait
GET  /list
POST /cancel
POST /cancel-all
POST /reveal
GET|POST /settings
GET  /events
```

即：`/download` 作为**端点**可以用，`/download/xxx` 作为**前缀**不行。

## 2. 受管程序的 cwd 不是它的数据目录

**现象**：受管引擎起来后，`tasks.json` 落到了意料之外的位置，或者干脆写不进去。

**排查**：把数据目录打印出来对比，发现 `process.cwd()` 指向 entry 的解析基准目录，
而不是 App 的 `dataDir`。

**根因**：`ctx.runtime.start({ entry })` 里 `entry` 是相对某个基准解析的，
受管进程的 cwd 随之确定，和 App 自己的数据目录没有必然关系。

**解法**：数据目录经 `args` 显式传入，受管程序从 `process.argv` 读：

```js
// app 侧
ctx.runtime.start({ runtime: "node", entry: "engine/server.js", args: [ctx.dataDir] })

// engine 侧
const DATA_DIR = process.argv[2] || process.env.HD_ENGINE_DATA_DIR || process.cwd();
```

不要依赖 cwd，也不要指望它等于 `dataDir`。

## 3. 就绪标记必须独占一行且精确匹配

**现象**：引擎已经监听端口、`/ping` 也能通，但宿主始终认为它没就绪。

**排查**：把就绪输出从 `HD_ENGINE_READY:4317` 改成裸的 `HD_ENGINE_READY`，立刻正常。

**根因**：`service.readyMarker` 是**行级精确匹配**，行里多任何字符（哪怕只是端口号）
都匹配不上。

**解法**：

```js
console.log(READY_MARKER);   // 独占一行，不带任何多余字符
```

注意：本项目后来把 `service` 整个去掉了（见第 4 条），此条对仍在用 service 的
场景有效。

## 4. `runtime.service` 会卡死 app 工具回包（最隐蔽的一条）

**现象**：App 的工具被模型调用后，`execute` 明明在 40ms 内就 return 了，
但模型侧收到的是：

```
App tool "xxx" failed: RPC callback.tools.execute timed out after 30000ms
```

而且工具的**副作用全都成功**（下载照跑、任务照建、结果照投递），只有回包超时。

**排查过程（关键在排除法）**：

1. 先怀疑 execute 太慢 → 日志显示 `returning | +39ms`，**排除**。
2. 再怀疑自己轮询引擎占住了 RPC → 把轮询改成读结果文件（纯 fs，不产生 RPC），
   **仍然超时**，**排除**。
3. 怀疑引擎或 service 长连接 → 写了三个探针工具做对照：

   | 探针 | 行为 | 结果 |
   | --- | --- | --- |
   | `hd_noop` | 什么都不做，直接返回 | **超时** |
   | `hd_log_only` | 只写一条日志 | **超时** |
   | `hd_task_only` | 只做一次 `ctx.tasks.create` | **超时** |

   三个探针日志的时间戳间隔正好 31 秒一个，说明每一个都吃满了 30 秒超时。
   **连"什么都不做"都超时** → 问题与工具内容、与 tasks、与引擎逻辑全都无关。

4. 把 `ctx.runtime.start({ service: {...} })` 整个摘掉再测 → **立刻不超时**。

**根因**：宿主 app-host 侧的工具执行体长这样（`app-host-entry.js` 约 L3461）：

```js
rpc2.handle(AppHostMethod.CallbackToolsExecute, async (params) => {
  // ...
  const result = token ? await runWithAppCallToken(options.pluginId, token, invoke) : await invoke();
  await rpc2.drain();          // ← 等所有挂起的 RPC 排空
  if (result instanceof Response) return http.serializeResponse(result);
  return result;
});
```

而 `drain()` 的实现是：

```js
async drain() {
  while (this.inflight.size > 0) {
    await Promise.allSettled([...this.inflight]);
  }
}
```

`ctx.runtime.start({ service })` 为了让宿主能代理 `/api/apps/<id>/routes/_runtime/<rid>/`，
会保持一条**常驻连接**。这条连接永远在 `inflight` 里，于是 `drain()` 永远转圈，
工具回包卡到 30 秒 RPC 超时。副作用在 `invoke()` 里早就做完了，所以功能看着正常。

**解法**：不用 `runtime.service`，改成**引擎自监听 + app 用 `ctx.network.fetch`**：

```js
// 1. 引擎自己监听回环端口（受管进程内）
server.listen(4317, "127.0.0.1", () => { ... });

// 2. app 侧经受控出网通道访问，清单顶层声明 network
const res = await ctx.network.fetch("http://127.0.0.1:4317/ping", { method: "GET" });
```

```json
"network": {
  "allowedHosts": ["127.0.0.1"],
  "methods": ["GET", "POST"],
  "allowLocalhost": true,
  "defaultTimeoutMs": 30000,
  "maxResponseBytes": 5242880
}
```

注意 `allowLocalhost: true` 必须显式写：缺省为 `false` 时 localhost 与私网地址一律拒绝，
且 HTTP（非 HTTPS）也只在声明了 `allowLocalhost` 后才放行。

前端（iframe 卡片）不能直接敲 4317（CSP + 白名单），另经 App 自己的路由转一手：

```
前端 → /api/apps/<id>/routes/engine/<path> → app 侧 ctx.network.fetch → 127.0.0.1:4317
```

## 5. App 工具的返回值必须是 `{ content: [...] }`

**现象**：不再超时之后，工具回包显示成：

```
(no tool output)
```

**排查**：对比宿主文档里的官方示例，发现返回值形状不同。

**根因**：模型的工具循环期望的返回形状是：

```js
return { content: [{ type: "text", text: "..." }] };
```

返回裸对象（如 `{ ok: true, taskId: "..." }`）宿主认不出，当成"没有输出"。

**解法**：所有工具统一返回该形状；需要给卡片或后续逻辑用的结构化数据放 `details`：

```js
return {
  content: [{ type: "text", text: "已开始下载：xxx\n任务 ID：yyy" }],
  details: {
    card: { route: "/card.html?taskId=yyy", title: "...", aspectRatio: "8:1", cardForm: "flush" },
    download: { taskId: "yyy", state: "pending", ... },
  },
};
```

`details.card` 是**聊天流卡**的触发点：宿主运行时透传，据此在工具块下方挂一个 iframe。

## 6. 聊天流卡的宽度上限 = 卡壳 `clientWidth`，随窗口浮动

> **⚠️ 本条已作废（2026-09-14）**：宿主 0.978.0 起，聊天流卡信封宽度上限从 300 提到 **774px**，
> 页面按 450 上报实测渲染 **449px**（上报值 −1px）。“宽度没有页面→宿主上报通道”的结论不再成立。
> 下方排查过程与当时的实测数据作为历史记录保留，请勿据此实施。
>
> 本文早期版本把这条写成了“宽度由宿主锁定，页面调不动”。那是**错的**，已按实测改写。
> 错误根源见本节末尾“方法论教训”。

**现象**：卡片里三个操作按钮挤成两行，想把卡片改宽。改了卡片上报宽度（`hana.ui.resize({width})`）
与卡片 CSS 的 `max-width`，从 470 调到 540 再到 620，**实测毫无变化**。

**排查**：先查宿主侧。bundle 里的 resize 桥（`resize-bridge` 脚本）只发高度：

```js
if (h !== last) { last = h; window.parent.postMessage({ type: 'hana.card-resize', height: h }, '*'); }
```

确实没有 width 这一维。但《APPS.md》的“尺寸信封”章节给出了权威规则（当前会推送的挂载位表）：

| 挂载位 | height | width |
| --- | --- | --- |
| 聊天流插件卡 | `flexible`，max 为聊天可视区高度上限 | `flexible`，max 为卡壳 `clientWidth` |
| 黑板 / 拆窗帧 | `fixed`，value 为容器 `clientHeight` | `fixed`，value 为容器 `clientWidth` |
| page / widget | `flexible` | `fixed`，value 为容器 `clientWidth` |

即：宽度**不是 locked，而是 flexible**，max 就是卡壳的 `clientWidth`。

**实测验证**：在卡片里直接量四个宽度（真渲染后量 `getBoundingClientRect`）：

```
iw347 dpr1.75 body347 root347 dl347 CW620
```

`body` / `#dl-root` / `.dl` 三者**全部等于 iframe 宽度**，说明容器已完全撑满；
`CARD_WIDTH` 620 够不到，所以从没参与。另一次在更大窗口下测得 `iw937`，
同样四值一致。结论：**卡片宽度 = 宿主 iframe（卡壳）宽度**，随窗口大小浮动。

**根因**（两条同时成立）：

1. 宽度**没有页面→宿主的上报通道**（resize 桥只认 height），页面对"宽于上限"无发言权；
2. 宽度**上限由卡壳 `clientWidth` 决定**，而卡壳宽度跟随宿主窗口/消息区，不是固定值。

**解法**：内容侧向既有宽度贴顶，布局按窄宽设计：

- 首行只放徐章 + 操作按钮（去掉元信息和百分比/大小），让按钮有完整一行可用；
- 按钮组用 `margin-left: auto` 推到最右，把空间用满；
- 百分比/大小与进度条同排（`.dl-row2`）；
- CSS 里把 `html` / `body` / 根容器显式 `width: 100%`，避免块级容器自己缩。

要"比上限更宽"，只能宿主把卡壳做宽，页面做不到。

**方法论教训**：这个坑排查了很久，主要陷在验证手段上。

1. **系统缩放会让截图量像素失真**。这台机器 `devicePixelRatio = 1.75`，截图上的像素
   比 CSS 像素大 1.75 倍。我拿截图目测“卡片约 230px”并据此连改三轮，全部改错方向。
   **先看 dpr，再信截图**。
2. **要数字就让页面自报**。在 DOM 里插一行字、或把值打进转发日志，比用截图目测可靠得多。
3. **测量时机比测量本身重要**。第一版诊断写在 `render` 拼字符串时，那一刻 `.dl` 还没插入
   DOM，量到的是 `0` 和“找不到”；挪到渲染后量才拿到真值。
4. **诊断字色要跟主题**。红字在深色卡上对比度极低，一直看不见，误判为“没生效”。
**说人话**：宿主只给了高度这一扇门，就别再去撞宽度那面墙。

## 7. iframe 里请求 app 自己的路由，必须带表面会话票据

**现象**：聊天流卡前端一直空白，引擎日志里没有任何请求。直接浏览器打开同一路由却正常。

**排查**：`/api/apps/<id>/ui/<file>` 手动请求，返回
`403 {"error":"forbidden","reason":"missing_credential","connectionKind":"local"}`。

**根因**：宿主给 iframe 签了一张表面会话票据，随 iframe URL 的 `appSurfaceSession` 下发；
iframe 内部发起的请求要把这张票据回传到 `X-Hana-App-Surface-Session` 头，
宿主才认它是这张卡发出的。不带就 403。

**解法**：静态页面启动时自读 `location.search` 里的 `appSurfaceSession`，
后续所有 fetch 都带上 `X-Hana-App-Surface-Session` 头。

**另一个同时踩到的**：iframe URL 里宿主还挂了 `hana-theme` / `hana-css`，
主题要自己读参数写 `data-hana-theme` 并挂上宿主样式表，否则卡片在一张白底里突兀地待着。

## 8. 卡片路由不能带 query

**现象**：卡片 `contributes.cards[].route` 写成带 `?taskId=xxx` 的路径，卡要么不渲染要么报错。

**根因**：卡片路由必须是 ui/ 下的**相对静态路径**，不能含 `?` `#` `..` `\`。
查询参数一律不行。

**解法**：route 固定为静态页（如 `/card.html`），需要参数就由页面自己向引擎问，
引擎在无参时回退到“最近一个任务”。本项目里 `/wait` 无 taskId 就回退，
另加 `hdboot` 在拼转发地址前剥掉基址前缀再映射。

## 9. 卡片宽度的两层归属：资源卡可覆盖，插件流卡不可

**缘起**：第 6 条查清了“插件流卡宽度由卡壳决定”，但宿主里有**两类长得像的卡**，
一开始把两者当成了同一个东西，白跑了两轮重启。这里把区分记下来。

**两类卡的对照**：

| 卡类型 | 外壳类名 | 宽度来源 | 可覆盖？ |
| --- | --- | --- | --- |
| **资源卡**（文件/链接预览那种） | `._card_cc83f` | `--chat-resource-card-width`（默认取任务族值） | ✅ 可覆盖 |
| **聊天流插件卡**（本项目的下载卡） | 无稳定类名（外壳在聊天流组件内） | `--chat-task-block-width`（任务族统一值） | ❌ 无开放口子 |

资源卡那条规则的原文（在 `assets/schedule-draft-*.css`）：

```css
._card_cc83f {
  --chat-resource-card-width: var(--chat-task-block-width, 348px);
  width: var(--chat-resource-card-width);
  max-width: 100%;
}
```

注意变量名里带 `resource`。**看到 `--chat-resource-card-*` 就知道是资源卡，不是插件卡**，
这是当初认错对象的关键。

**实测证据（可复现）**：

1. 往 `styles.css` 末尾追加 `._card_cc83f { width: 520px !important }`；
2. 重启宿主；
3. 资源卡**当场变宽**（会话里的文件预览卡）；
4. 还原文件并再重启，资源卡**恢复原宽**。

而同一时间段里，聊天流的下载卡宽度**纹丝不动**，始终 348。
两件事在同一批重启里发生，对照非常干净。

**为什么“借”不过去**：资源卡和插件卡走的是两套独立容器，没有共用血缘。
想让插件卡也宽度可控，得让它的外壳也用上资源卡那套类/变量，而外壳结构与类名都在
宿主渲染代码里，页面侧碰不到。另外，**插件卡确实能变宽，但只能改共通的任务族变量**
`--chat-task-block-width`，代价是工具条 / Subagent / Workflow 卡一起变宽（连坐）。

**顺带踩到的坑：CSS 加载顺序**

宿主 `index.html` 里的样式表顺序是：

```html
<link rel="stylesheet" href="styles.css">          <!-- 先 -->
...
<link rel="stylesheet" href="assets/schedule-draft-*.css">  <!-- 后 -->
```

两张表里都有 `._card_cc83f` 规则时，**后加载的胜**。所以往 `styles.css` 末尾追加
同名覆盖是无效的（被 schedule-draft 盖回去），表现得像“改了没反应”。必须用
`!important` 才能压过，因为原规则本身不带 `!important`。

**方法论教训（这条比结论值钱）**：实验“没效果”时，先问自己**是不是打错了靶子**。
本项目这次的真相是：覆盖生效了，只是作用在另一类卡上，而我盯着的那张卡本来就不归它管。
验证时应该**同时观察两类卡**，只盯一个很容易把“生效在别处”误判成“完全没生效”。

## 10. 卡片宽度只吃容器：宽度上报对 v2 应用卡不生效

> **⚠️ 本条已作废（2026-09-14）**：宿主 0.978.0 起，宽度上报**已经生效**：
> 信封上限 774px，页面按 450 上报实测 **449px**（上报值 −1px），与容器宽度、消息是否带文字均无关。
> 简而言之，当时缺的那段“上报值→卡壳宽度”的接线，在 0.978.0 补上了。
> 下方排查过程（含那套带数字的宽度探针方法）作为历史记录保留，**方法仍值得沿用**。

**现象**：`CARD_WIDTH` 从 470 一路调到 620，卡片宽度毫无变化；偶尔又看着很宽，规律说不清。

**排查**：给卡片插宽度探针（左上角浮层显示 `上报值>window.innerWidth`），同代码、同窗口，只改消息构成与上报值：

| 卡片 | 消息构成 | 上报值 | 实测宽度 |
| --- | --- | --- | --- |
| t1 / t2 / t4 | 纯工具调用（消息里没有文字） | 451 | **347** |
| t3 / t5 | 消息里有文字 | 451 | **649** |
| t6 / t7 | 消息里有文字 | 200 | **649** |

**根因（实测）**：

1. **`ui.resize` 的 width 对 v2 应用卡不生效**：上报 200 和 451，实测都是 649（有文字时）；451 在纯工具调用时实测 347。宽度与上报值无关。宿主插件 iframe 组件里确实有 `Math.max(50, 上报值)` 的 width 采纳逻辑，但在这条挂载路径上没落到卡壳，断点待与宿主确认。
2. **卡片宽度 = 容器宽度**，容器随窗口/布局变化：消息里有文字 → 聊天流当前给出的列宽（实测到过 649 和 1018）；纯工具调用 → 347（工具块 `--chat-task-block-width: 348px`）。同一会话里两张卡宽度不同（649 / 1018），说明容器按渲染时刻的窗口状态取值。

高度不受影响，它走宿主注入的 `hana.card-resize` 桥（只报 height），与宽度是两条独立通道。

**解法**：App 侧对宽度没有话语权（挂载容器由宿主渲染层决定，manifest 与 `details.card` 里没有控制它的字段）。能做的两件事：

1. **Agent 侧**：触发下载前先输出一句文字，卡片从 347 提到 649（09-12 实测有效）；
2. **宿主侧**：要让宽度真正可控，需宿主修两处（接上 ui.resize 的 width，或让卡片恒定挂普通消息块）。

**方法论教训（这次比结论值钱）**：目视读数在这件事上反复出错（把 649 读成 599 之类），错误读数一度支撑了「上报生效」的错误结论。带数字的探针（而且把上报值和实测值一起显示）才是可信证据。

## 附：验证方法的教训

这三条不是宿主坑，是排查方法上的坑，但同样值得记：

1. **副作用成功不等于调用成功。** 投递、建任务、下载全都正常，工具回包照样可以超时。
   报错文本里的 "failed" 说的是回包，不是功能。别被它带偏。

2. **对照实验优先于推理。** 这个 bug 单靠读代码推不出来。写一个"什么都不做"的探针，

## 11. 聊天流卡片投递：宿主 0.970.9 的两处断点（2026-09-13）

**现象**：`details.card` 里一切正常（pluginId / route / preferredWidthPx 都进了 jsonl），
聊天流里既没有卡也没有报错；分层心跳 `/hb-cardhtml` **0 次命中**，证明 card.html 从未被 iframe 加载。
会话重载后卡片全消失。

**排查**：
- 卡片资源 `/api/apps/hana-downloader/ui/card.html` 返回 200；`/api/apps/cards` 里 `progress` 卡已注册、routeUrl 正确。
- `show_card` 内联卡能正常渲染 → 聊天流卡片管道本身没坏。
- `/api/sessions/messages` 的 blocks 里一条 `plugin_card` 都没有。

**根因（已用宿主运行时诊断钉死，详见 `宿主缺陷-v2应用卡片投影丢工具名.md`）**：

1. **v2 应用工具的真实名字在投影时丢失**（卡片消失的直接原因，断点比早前推断更靠前）。
   宿主投影时用 `J_t(t, e)`（bundle ~53560）取工具名：当 `t === "tool_call"` 时去
   `e.details.bridgedTool.name` 取真名 —— 而 `bridgedTool` 是宿主**只给 MCP/连接器工具**注入的
   （`cte()` ~172427，值为 `{name, server: ownerId}`）；SDK 桥接的 v2 应用工具结果里没有这个字段，
   名字就停在泛化名 `"tool_call"`。
   在归属解析 `voe()`（~53498）内插诊断后实测，重启触发若干工具调用，66 次投影调用的查询键分布为：

   ```
   exec_command:29  loop_control:9  tool_call:6  write:6  read:5
   write_stdin:4    edit:3    web_search:2  grep:1  ls:1
   download-*: 0    ← 一次都没有
   ```

   同期名册内容本身**完全正确**：
   `hana-downloader(loaded, names=[download-file|download-wait|download-cancel|download-command])`。
   但拿 `tool_call` 去查 → 所有 app `owns=false` → `matched=[]` → owner=null。
   owner=null 时 `Z_t()` 仍产卡，只是**不带** `channel:"app"`；随后被 `Qoe()`（~53611）过滤掉
   （无 channel 的卡要求 `pluginManager.getPlugin(id)` 存在，v2 应用不在 v1 插件表）→ **静默丢弃**。
   前端 `jl()` 里 `x = e.channel === "app"` 因此永远为 false。

   > **修正早前推断**：本节初稿写的“v2 App 工具运行时注册、名册查不到”是**错的**。
   > 名册里有名字，丢的是**查询键**（工具真名被泛化成 `tool_call`）。宿主内置工具
   > （`exec_command`/`read`/`write`…）用的是真实名，能正常进投影 —— 但它们不归任何应用所有，
   > `owns=false` 属正常，不能据此判断名册坏了。
2. **历史投影缺口**：`details.card` 不进历史重建；而 v2 App 唯一可用的官方流内卡通道
   `session:send-custom` 在**会话 streaming 期间**会被排成 `followUp` 队列
   （返回 `{ok:true, mode:"followUp", entryId:null}`），实测该队列不落进会话历史。
   工具调用必然发生在 streaming 期间，所以从 App 侧永远打不中“会话空闲”这个窗口。

**已尝试并排除**：
- `legacySessionPath` 定位：宿主 `eo()` 对 app caller 会把它交给 `SessionManifestResolver.resolve()`，
  而那里只认 `sessionPath`/`path`（`p5t()` 实现），`legacySessionPath` 被丢 → 报
  "Session manifest resolution requires sessionId or legacy sessionPath."。
  **用 `callToken` 定位是正解**（SDK 的 `AppSessionAddressOrCallTokenV2` 支持）。
- 跨会话投递必须显式 `scope:"all"`，否则报 `session "..." does not belong to app "..."`。
- 延后投递（setTimeout 25s）绕开 streaming：**callToken 有寿命**，过期后报
  `passed a callToken that is unknown, expired, or not minted for this app`。
- `delivery:"next-step"`（想走 steer 分支）：`session:send-custom` 的 handler 只把 `triggerTurn`
  传给 `deliverCustomMessage`，`delivery` 字段被丢弃 → 仍是 followUp。

**结论**：App 侧没有可靠手段让卡片进聊天流。修需宿主改两处之一：
`resolveToolOwner` 认得 v2 App 运行时注册的工具；或让 `session:send-custom` 在 streaming 下也落盘
（并把 `delivery` 传下去）。在此之前，下载器的对外形态是**卡片中心那张常驻卡**
（`/api/apps/cards` 里 id=`manager` 的卡，可看全部任务与进度），功能完整，只是不在聊天流里。

**顺带记两条宿主操作姿势**（比 UI 好用）：
- 批准 App 声明：`POST /api/extensions/<ref>/reload` → 返回 `{status:"awaiting_confirmation", staged:{stagedId}}`
  → `POST /api/extensions/staged/<stagedId>/confirm`。ref 形如 `app:hana-downloader`。
- 热重载 App：`POST /api/extensions/app:hana-downloader/reload` 直接返回 `ok:true`（声明未变时）。
  **但热重载会掐断会话侧的工具 RPC**（`RPC peer closed`），改完代码要验证工具必须重启宿主。

## 12. 会话自循环：往自己会话里投消息 = 对着麦克风开音箱（2026-09-13）

**现象**：连续收到 138 条内容完全相同的「下载 probe11.json」指令，每条都照做、每次都成功。
看起来像用户在刷屏，实际对面没有人。

**定性证据**（会话 jsonl）：
- 真实用户消息（`role: user`）全文件只有 **12 条**，其中没有任何一条是「下载 probe11.json」。
- 那 138 条全是 `type: custom_message`、`customType: app:hana-downloader/download`、
  `content: "下载 probe11.json"`、`display: true` —— 正是本 App 自己投递的卡片文本。
- 每一轮 `custom` / `turn_input_consumption` 的 `data.deliveryId` 形如
  `deferred-delivery:app:hana-downloader:<taskId>:<uuid>`，把投递与下一轮输入直接对上。

**根因**：`session:send-custom` + `display: true` 投出的 custom_message 会被宿主
**当作「本轮之后的新输入」**（streaming 时排成 followUp，空闲时作为下一轮输入），
于是唤醒 Agent → Agent 又调用工具 → 工具又投一条 → 死循环。
`triggerTurn: false` **挡不住**这条路径。

**为什么长时间没被发现**：投递进到 Agent 上下文时，外壳与真实用户消息完全一致
（同样的角色呈现、同样的位置），从 Agent 视角看不出差别。
**唯一可靠的判别方式是查会话记录里的 `role: user` 计数**，而不是看消息长得像不像。

**解法**：不要往自身会话投递会触发新一轮的消息。若确实需要投递展示型内容，
必须满足其一：
- 确保它不会被当作输入（宿主侧需提供真正的 display-only 通道）；
- 或在 App 侧加“只投一次”的护栏（例如按 taskId 去重 + 会话级熔断计数），
  但这个护栏治标：真正的判定权在宿主。

**教训（比结论值钱）**：同一指令短时间重复出现 ≥3 次且内容完全一致时，
**不要继续照做** —— 立即核对来源（jsonl 里 `role: user` 有没有对应条目）。
“用户没回我的追问”本身就是最强信号：真人不会连发一百多次同一句、其他什么都不说。

**后续（2026-09-13 重构）**：这条通道最终被保留为唯一可用的出卡通道，代价用三道护栏压住：
内容恒为 `【下载记录】` 开头的记录句、按 taskId 去重、每小时 30 条熔断，
并在下载铁律里显式告知模型「以【下载记录】开头的是系统记录，不是用户指令」。

## 16. 卡片高度被一句"保护性下限"钉死：`if (h < 40) h = 40`

**现象**：内容已经压到 32px，聊天流里却始终是 40px，进度条与卡片下边框之间留着约 8px 空白。
改按钮尺寸、改字号、改 padding 全都动不了那 8px。

**排查**：给卡片加尺寸诊断（`hana.track` 上报 `window.innerHeight` + 各行 `offsetHeight` + 计算样式），
数据立刻暴露三层不一致：`h=40` 而 `bodyH=dlH=32`。顺着上报函数找到硬下限：

```js
let h = Math.ceil((dlEl ? dlEl.offsetHeight : …) + pad);
if (!isFinite(h) || h < 40) h = 40;   // ← 罪魁：内容再小也报 40
```

**根因**：这行本意是"至少留出可点高度"，但它把**上报值**锁死在 40，宿主于是永远把 iframe 撑到 40。
**保护性下限一旦被当成测量结果，就成了天花板**——而且它长得像正常代码，没人会怀疑。

**另一处连带坑**：`body` 主规则里有一条后写的 `font-size: 14px`，会盖掉文件顶部
`html, body { font-size: … }` 那条。压行高时只改顶部那条**完全不生效，且不报错**——
CSS 同权重规则后写者胜。诊断里 `bodyCs.fs` 一直显示 14px 才把这个揪出来。

**解法**：

1. 下限从 40 降到 24（真没内容时仍留可点的两行）；
2. 根字号写进 `body` 主规则，或确保没有后写覆盖；
3. 诊断项从"只看总高"扩展到"每行 `offsetHeight` + 计算样式"——一次就能看出差在哪一层。

**结果**：45 → 40 → **32px**，`h`/`bodyH`/`dlH` 三层对齐，无余量。

**方法论**：卡片高度这类问题，光看最终上报值会一直在错误的地方打转。
**要分层看（iframe 高度 / 根元素 / 每一行），再对照计算样式**，两分钟定位。

## 17. 遗留的 pending app-task 会挡住短定时（loop 闹钟定不上）

**现象**：想定 60 秒的唤醒闹钟被拒：

> Background work in this session wakes it automatically on completion; do not schedule alarms
> to poll it. While background work is live, alarms must be long fallbacks (>= 1200s).

但当时并没有在跑的下载，看起来也没有占位。

**排查**：`check_pending_tasks` 列出会话全部 deferred 任务，发现有 **6 条 `status: "pending"` 的 app-task**
（形如 `app:hana-downloader:<uuid>`）。共同点：**都是宿主被重启时正在跑的任务**——
下载中途重启，宿主侧那张任务账单没收到终态（`tasks.complete/fail/cancel`），就永远挂在 pending。

**根因**：宿主判定"后台工作是否活跃"时，把**未终态的 app-task**也算作活跃工作，
因此只允许长兜底闹钟（≥ 1200s）。而这个"活跃"与"是否真的在下载"无关——
引擎侧的任务早在重启时就没了，剩下的只是宿主侧的账。

**解法**：`stop_task(task_id)` 逐条终止。清完全部 6 条后，**60 秒闹钟立刻能定上并准点触发**。

**给 App 的教训**：**重启宿主前，先让在跑的任务落终态**，否则会在宿主侧积压 pending。
App 侧目前没有自动回收手段，只能手动 `stop_task` 或等宿主超时。

**顺带**：`check_pending_tasks` 是查这类问题的正确入口——`resolved` / `failed` / `pending` 一览无余，
比翻日志快得多。

## 18. 卡片里的 App 别自己铺底色；宿主主题变量也不注入 iframe

**现象**：下载管理器的底色看起来比同屏的宿主原生卡（llama 监视器）暖一档，像「多了一层底色」。

**排查**：

1. 管理器 `#dl-root` 写的是 `background: var(--bg-card, var(--bg, var(--mgr-bg, #FCFAF5)))`，
   兜底 `#FCFAF5` 恰好等于宿主 `--bg-card` 的值，照理应当一致；
2. 但**宿主主题 CSS 并不注入 App 的 iframe**——页面只 `<link>` 了自己的 CSS，
   所以 `var(--bg-card)` 永远取不到，实际落地的是兜底值；
3. 兜底值再叠在**宿主卡片容器已有的底色**上，两层一叠就显出偏差。

**正解**（参照 llama-monitor，也是跑在宿主卡片里的 App）：**底色交给宿主容器**，
页面自己透明；只有内部区块（卡片、条带）才用变量或自包含色。

```css
/* 错：自己铺一层，叠在容器上 */
background: var(--bg-card, var(--bg, var(--mgr-bg, #FCFAF5)));
/* 对：透明，容器是什么色就是什么色 */
background: transparent;
```

**教训**：App「自包含色板」是为了抗宿主变动，但**底色这一层必须让给容器**——
否则永远对不齐，而且宿主换主题时只有你不变。

**顺带**：同屏找一个参照物（另一个卡）比对着 CSS 猜快得多。

## 19. 宿主缓存 App 的 iframe 页面：reload 之后页面并不会重新加载

**现象**：给管理器页加了诊断代码，同步 + reload 都成功、HTTP 拉取也确认已含新代码，
但页面报出来仍是旧逻辑（诊断始终不上报）。

**结论**：**reload 不会让已挂载的 iframe 页面重新执行脚本**。
文件确实换了，HTTP 也提供新版（`Cache-Control: max-age=0, must-revalidate`，ETag 随文件变），
但页面的 JS 上下文还是旧的。

**解法**：**改 UI 代码后重启宿主**，不要只 reload。
这也解释了早先改 `card.css` 时 reload 无效、必须重启。

- 第 14 条：reload 会断**工具 RPC**（改工具逻辑要重启）；
- 本条：reload 不刷新**页面**（改 UI 也要重启）；

## 20. 后台结果 interlude：App 侧没有隐藏口子，等宿主开放（2026-09-17）

**现象**：下载完成后，聊天流除进度卡外还有一条居中提示「<agent 名> 收到了来自 app-task 工具的结果」。

   SDK 的 bus verb 表（`app-contract/bus-requests.js`）无呈现控制类 verb，宿主设置里也没有开关。

**机制要点（对我们有用的部分）**：interlude 属**呈现层，与投递解耦**。同一条 custom_message

## 22. winget 管道模式实况与 HRESULT 退出码（2026-09-18）

## 25. winget 下载的网络表现与排查路径（2026-09-18 实况）

1. 先走 **DeliveryOptimization（DO）**：60 秒无进展即抛错（日志 `DODownloader.cpp(339)`，

**排查路径**（下次 winget 任务卡住时按这个走）：

- winget 诊断日志：`%LOCALAPPDATA%\Packages\Microsoft.DesktopAppInstaller_8wekyb3d8bbwe\LocalState\DiagOutputDir\`

- 进程连接：`Get-NetTCPConnection -OwningProcess <winget pid>`（看有没有到下载域名的连接）；

  数分钟不动，DO 通道处于瘫痪态）；
- 对照实验：`curl.exe -L` 直下 manifest 里的 InstallerUrl（`winget show <id>` 可见），
  区分“网络问题”与“引擎问题”。

**环境事实**：本机到 github.com 的连通性时好时坏（同晚 20:32 通 → 20:35-20:42 断 →

## 27. Node 自建 CONNECT 隧道的两个坑（2026-09-18）

给“经代理的 https 请求”写隧道（engine/tunnel-agent.js）时连续踩了两次，留档：

1. **`https.Agent.createConnection` 必须回传“已完成 TLS 的流”**——Agent 不会对你
   返回的流再做 TLS。只回传 CONNECT 裸 socket → 请求挂死（等 TLS 握手 20s+ 超时，
   报 `socket disconnected before secure TLS connection was established`）。
2. **不要用 `http.request({ method: "CONNECT" })` 发隧道请求**——它的 connect 事件
   给的 socket 上直接 `tls.connect` 会挂死（socket 经 http 解析器后状态异常）。
   正确姿势：**raw `net.connect` 手写 `CONNECT host:port HTTP/1.1` 字符串，
   自己按 `\r\n\r\n` 解析响应，再在原始 socket 上 `tls.connect({ socket, servername })`**。
3. 修复后双场景验证：HEAD 302 秒回（595ms）、探测 HEAD 拿 Content-Length 1035264 正确。
   此模块同时修复了 URL 下载的代理隧道（此前经代理的 https 下载可能同样挂死）。

## 29. 命令类任务的 `received/total` 是「计数」不是字节（2026-09-19）

**根因**：进度解析器给 `git-clone` / `pnpm-install` 的 `received/total` 是**对象数/包数**，
不是产物大小：

- git clone：`Receiving objects: 57% (8/13)` → `unit="objects"`，13 是对象数；
- pnpm：旧实现按行内百分比反推包数，分母是常量 `PACKAGES_TOTAL`（1000），不是真实包数，
  `unit="packages"`（2026-09-19 已改为不设分母，见第 30 条）。

只有 URL 下载的 `received/total` 才是真字节。

**症状**：任何「把 received/total 当字节渲染」的分支都会撒谎——结算文案曾输出
`下载完成：verify-pnpm / 大小：1000 字节`（实为 1000 个包计数），卡片与管理器的
完成行也把 13 / 1000 按 B 显示。

**修法（2026-09-19）**：结算文案按三类分措辞——URL 下载报路径+字节；
命令类（git clone / pnpm）只报路径（「克隆完成」/「依赖安装完成」）；
包安装（winget / pip）报 note。管理器的完成行不再对命令类渲染字节。
取消/失败文案动词同步按类型取（克隆 / 安装 / 下载）。

**下次加新任务类型时的自检**：这个类型的 `received/total` 是字节吗？不是，就别让它
进任何字节渲染分支（结算文案 / 卡片数字组 / 管理器 meta 行）。

## 30. pnpm 的进度数据实况：没有「常量分母」这回事（2026-09-19）

**实测**（pnpm 11.21.0，管道模式，`node pnpm.mjs install`，Start-Process 保真重定向）：

- 输出**逐行、无 `\r` 重绘**（旧注释里写的「pnpm \r 重绘每秒多次」在 11.x 的
  append-only reporter 下不成立）；
- 进度行只有一种形态：`Progress: resolved 31, reused 12, downloaded 19, added 0`；
- **`Packages: +N` 在下载阶段不出现**，要等进入链接阶段才打印——网络卡住时全程没有，
  也就是**总包数不可知**；
- 中文系统的 `Update available!` 提示框（花边框）会混进 stdout，解析器必须返回 null 而不是误判；
- 实测时 registry.npmjs.org 持续 `error (23)` 重试，全程停在 fetching 阶段（根因与修法见第 31 条）；

**旧实现的病**：拿常量 `PACKAGES_TOTAL = 1000` 当分母，再用伪造的 pct 反算 received，
于是「1000 包」这个数字从头到尾都是编的，并顺着结算文案一路漏到用户眼前。

**新实现（本次）**：

- `received` = 已装 > 已下载 > 已解析（单调不减，偶发的计数重置不会让进度倒退）；
- `total` 只在真拿到 `Packages: +N` 时才有，`pct` 随之才有；
- 没有 total 就不给 pct（卡片进度条走不确定态），另给 `detail`「解析 X · 下载 Y · 已装 Z」；
- `postinstall` / `Done in` 不再伪造 90% / 100%（无分母时只推进 stage）。

**联动改动**（分母一个概念，牵动四层）：

1. `dlcore` 消费逻辑改为**字段各自独立更新**——旧写法要求 `pct` 与 `total` 同时存在，
   会把「只有真实计数」的解析结果整个丢掉；
2. `dlcore` 的完成对齐（`received→total` 反推）只对**字节型**做，计数型不反推，
   否则完成时会凭空出现「19/19 包」这种假分母；
3. `snapshot` 新增 `stageDetail`；卡片信息行优先显示计数明细；
4. 管理器运行行按 `unit` 渲染（`objects/files/packages` 用中文单位，不再走字节格式化）。

**下次碰到「进度条分母」类改动的自检**：这个分母是数据里给的，还是我选的？选中来的那个，
迟早会被当真。

## 31. pnpm 不读 Windows 系统代理，必须注入环境变量（2026-09-19）

**症状**：pnpm 任务卡在 fetching，反复 `[WARN] GET https://registry.npmjs.org/… error (23).
Will retry in 10 seconds`，长时间没有 `Done in` 行，停滞监视器最终报「连接停滞」。

**定位**（同一时刻、同一 URL，三路对照）：

| 通道 | 结果 |
| --- | --- |
| 直连 `registry.npmjs.org`（绕过代理） | 超时（30s，http=000） |
| 经 `127.0.0.1:7890` | **200，0.4s，36KB** |
| 系统代理开关 | 已开（`ProxyEnable=1`，`127.0.0.1:7890`） |
| 环境变量 `HTTP_PROXY/HTTPS_PROXY` | 空 |
| `npm config get proxy/https-proxy` | `null` / `null`（registry 为官方源） |

**结论**：Node 生态（pnpm）**只认环境变量代理，不读 Windows 系统代理设置**；本机直连 npm 官方源
不通，于是 pnpm 无限重试。同一台机器上 winget 恰好相反（跟随系统代理、日志里明写
`Default proxy is not set`，见第 25/26 条），pip 走 `urllib.getproxies()` 读注册表也跟随系统代理。

**修法**：引擎 spawn command 子进程时，对 `pnpm-install` 注入
`HTTP_PROXY / HTTPS_PROXY / http_proxy / https_proxy`（取 `resolveProxy`：环境变量 >
config.json > 系统代理注册表），并设 `NO_PROXY=localhost,127.0.0.1,::1` 避免回环流量绕代理。
其他链路不注入。

**验证**（实测，设上环境变量后）：同一安装 4.4s 完成，exit=0，并抽到完整成功输出形态：

```
Progress: resolved 21, reused 21, downloaded 0, added 0
Packages: +25
+++++++++++++++++++++++++
Progress: resolved 25, reused 25, downloaded 0, added 25, done
Done in 4.2s using pnpm v11.21.0
```

两个易错点：① 进度行结尾可能多一个 `, done`（`added 25, done`），正则不能锚定行尾；
② `Packages: +N` 出现在链接阶段，这就是总包数的唯一来源（接第 30 条）。

**通用教训**：判断一个 CLI 走不走代理，别按「它是个命令行工具」一概而论，按网络栈分类。
2026-09-19 用本地假代理逐个体检的实测表见第 33 条（curl / npm / pnpm / pip / uv / git 都读环境变量代理；
winget 反过来，只跟随系统代理；「Python 读注册表」当时只是推测，未实测）。

**同日复核（重要修正）**：本条前半段「直连超时 30s」只是当时那一瞬的网络快照，
不代表长期状态。后来重测发现直连是**不稳**而非**不通**：curl 单独请求 registry.npmjs.org 能 200（0.8s），
但 pnpm 并发拉包时频繁 `error (23)`，B 组对照实测甚至出现「单请求耗时 70.9s / 71.1s」。
所以注入代理的收益不是「从不通到通」，而是**从抖到稳**。

- 引擎原来取末尾三行，于是用户看到的失败原因就是 `No authorization header was set for the request.`，
  对一个查无此包的场景等于什么都没说；
- 另一个坑：pnpm 出错退出时 stderr 会冒 libuv 断言
  （`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)`，直接跑时退出码甚至是异常码），
  那是退出噪音，不是根因。

**修法**：失败摘要优先取含 `ERR_[A-Z0-9_]+` 或 `fatal:` 的那一行，取不到再退回尾部三行；
并对能确定语义的码补一句人话（`ERR_PNPM_FETCH_404` / `ERR_PNPM_NO_MATCHING_VERSION` /
`ERR_PNPM_META_FETCH_FAIL` / `ERR_PNPM_PEER_DEP_ISSUES` / git 的 `fatal: repository … not found`），
不做过度翻译。修后同一场景输出：
`[ERR_PNPM_FETCH_404] GET …: Not Found - 404（包或版本不存在，检查包名）`。

**通用教训**：CLI 的错误输出里，“最后一行”往往是最不具体的那个；摘要要按**错误码**找，
而不是按**时间**找。

## 33. 各 CLI 的代理行为：实测表 + 一个不依赖外网的测法（2026-09-19）

**测法（推荐）**：本机起一个「假代理」，把 `HTTP_PROXY`/`HTTPS_PROXY` 指向它，看工具会不会把请求交给它。
两种形态各有用处：

- **拒绝式**（回 502 并记账）：判定「读不读环境变量代理」，**不需要外网**，结果确定性最高；
- **透明转发式**（记账后转发给真代理）：判定「经代理能不能走通」。

**实测表：是否读环境变量代理**

| 工具 | 读 env 代理 | 证据 |
| --- | --- | --- |
| curl | ✅ | 假代理日志 `CONNECT registry.npmjs.org:443` |
| npm | ✅ | 同上 |
| pnpm | ✅ | 透明代理日志 `CONNECT registry.npmjs.org:443`（来自 pnpm） |
| pip | ✅ | 假代理日志 `CONNECT pypi.org:443` |
| uv | ✅ | 假代理日志 `CONNECT pypi.org:443` ×4 + `tunnel error: unsuccessful` |
| git | ✅ | 假代理日志 `CONNECT github.com:443` |

**系统代理跟随**

| 工具 | 跟随 Windows 系统代理 | 证据 |
| --- | --- | --- |
| winget | ✅ | 第 25/26 条：系统代理开→下载成功；日志里写着 `Default proxy is not set`（说明它不读 env） |
| pnpm | ❌ | 系统代理开着且 env 为空时走直连并卡死（8:17 实测） |
| 其余 | 未测 | 不做推测 |

**这次踩到的两个探针陷阱**

1. **拿 `pnpm view` 当探针会被本地 metadata 缓存骗**：它不发请求，于是假代理日志里没有记录，
   我险些据此写下「pnpm 不读环境变量代理」的错误结论。探针必须用真正会联网的动作
   （如 install 一个未缓存的包）。
2. **自制转发代理转发 TLS 隧道不稳**（实测 ECONNRESET）：别拿它当「经代理能不能走通」的判据，
   要验通不通就直接指向真代理。

**同批实测到的网络事实**（供以后判断“是不是网络的锅”）：

- 直连 `registry.npmjs.org`：单请求能 200（0.8s），但并发拉包频繁 `error (23)` / `ECONNRESET`，
  单请求最坏 70s+；经 Clash 稳定在秒级；
- `github.com` 直连 8s vs 经代理 1s；`pypi.org` 直连 0.74s、经代理 1.4s；
- 源不可达（registry 指向死端口）时 pnpm 报 `error (unknown)` 并按 10s / 1min 退避重试，
  `.npmrc` 里的 `fetch-retries=0` 没能止住重试。

## 34. 清账一轮：死代码判定，与两条「实现完整却没入口」的接线（2026-09-20）

**背景**：9-19 盘代码现状时列出四条「功能写完了但没有任何入口」和一批无调用方的方法。本轮做决断。

**删掉的（全在 `engine/dlcore.js`，删前全仓 grep 无调用方）**

- `prepare()` / `startPending()`：延迟启动链路。删后 `pending` 状态只剩防御分支（历史数据可能带）。
- `onceFinal()` 与 `_finalWaiters`：wait 的即时唤醒机制。app 侧早就改成轮询 `finished/` 文件，这条路没人走。
- `markDelivered` / `markConsumedByWait` / `markWaitActive` / `markWaitInactive` / `markWaitBudgetExhausted`：
  连同快照与持久化里的 `consumedByWait` / `waitActive` / `waitBudgetExhausted` / `delivered` / `deferredRegistered` 字段一起删。
- 速度缓存（`recordSpeed` / `getHostSpeed` / `speed-cache.json`）：**只写不读**——写了两周，没有读者。
- `/events` SSE 通道与 `broadcast`：引擎一直在推，没有消费者；终态与停滞本来就落盘给 app 读。

**接上的（引擎侧早已实现，只是没调用方）**

- 限速 `speedLimit`：`download-file` 新增 `speedLimit` 参数（字节/秒），透传到内核的 chunk 节流。
- 校验 `expectedSha256`：`download-file` 新增该参数，落盘前比对；不匹配判 failed，**不交付文件**。

**顺手收掉的两处内部不齐**

- 引擎端口原本两个来源（`index.js` 写死 4317 / `server.js` 读环境变量）→ `engine/engine-port.js` 一个常量，两边共用。
- 阶段文案、计数单位、「这是什么形态的任务」原本在 `index.js` / `ui/card.js` / `ui/manager.js` 各一份
  → `ui/shared/display.js`（Node 侧也 import 它）。

**实测**：`node tests/run-tests.mjs` 全绿——解析器 46 项、探测 10 项、展示 32 项、下载内核 17 项。
内核那 17 项里专门验了限速真的拖慢（1MB @ 256KB/s 用时 ≥3s）与 SHA-256 的对/错两条路。

**判断口径**（供后人复用）：删一个「没人调用」的方法前，先做三件事——
grep 全仓（含 md 里的示例与文档）、确认它不在持久化字段的读写环里、确认删掉后老数据不会被读成异常态。

## 35. 并发队列的一个初值坑，与「App 往用户会话投消息」的权限门槛（2026-09-20）

### 坑 1：新任务的 state 初值不能是 running

加并发上限时，`_createTask` 里沿用了没有队列时的老写法，把 `state` 直接初始化成 `"running"`。
结果 `_enqueueOrStart` 一检查 `_runningCount()`，把**刚创建的这个任务自己**算进去了：
`maxConcurrent=1` 时 `1 >= 1` 成立，于是第一个任务也被塞进队列。
表现是三个任务全部 pending + queued，谁都不动，一条报错都没有。

修法：`_createTask` 给中性初值 `"pending"` + `queued: false`，由 `_enqueueOrStart` 决定
是立刻 `_startTask`（state → running）还是挂进队列（queued → true）。

**判据**（可以推广）：凡是「先把对象建出来、再决定它算不算占资源」的地方，
初值都不该已经占着资源。否则"检查资源"的那一步会把自己数进去。

### 坑 2：App 往用户会话投自定义消息，默认投不进去

重试任务跑完要通知 agent。工具发起的任务靠宿主任务面（`sdk.tasks`）回执，那条路要 callToken，
而管理器里的按钮是 UI 发起的，没有 callToken。所以改走 `session:send-custom`。

它默认投不进去。宿主在处理这个 verb 前会取目标会话的 `ownerPluginId`，与调用方的 appId 比对，
而 `scope` 缺省是 `"own"`，不匹配就直接抛：

```
session "..." does not belong to app "hana-downloader"
```

要投进用户自己的会话，必须显式传 `scope: "all"`；此时宿主再查两项能力：
`app/sessions.manage`（该 verb 内部固定用 access=manage）与 `app/session.start-turn`
（会话正在流式中，或 `triggerTurn !== false` 时）。这两个能力清单里都已声明，所以能走通。

三个要点：

- `customType` 会被宿主加上前缀变成 `app:hana-downloader/<name>`。别用 `download` 这个名字——
  清单里的 `contributes.messageRenderers` 声明着它，会把消息渲染成一张多余的卡片。
  用 `retry-note` 这种不映射卡片的类型。
- `display: false` 只控制不上屏，消息照样进模型上下文；要唤起一轮 agent 得靠 `triggerTurn: true`。
- 投递目标用 `sessionPath`（App 工具的 execute 上下文里只有 sessionPath，没有 sessionId），
  宿主会自己把它解析成稳定的 sessionId。

## 36. 卡滞要「叫醒」，但 App 往会话投递只有一条路可走（2026-09-20）

**背景**：第三方七象限测试暴露「卡滞只落盘不通知」（见报告补记）。设计要求是：卡滞属于
「需要 agent 决策」的状态，判定后尽快让 agent 知道；但这类信息没重要到值得打断，
拼进会话、等下一次调用读到即可。

### 一、宿主投递分两条路，语义完全不同

读宿主 0.1013.2 的 `deliverCustomMessage(path, msg, opts)`：

- **会话流式（模型正在跑）**：按 `opts.delivery` 决定
  - `delivery: "next-step"` → `mode: "steer"`，当前回合的下一次请求就带上
  - 其他（含缺省）→ `mode: "followUp"`，排到本回合结束后
- **会话空闲（模型已停）**：按 `opts.triggerTurn` 决定
  - `true`（缺省）→ 起一轮（唤醒）
  - `false` → `mode: "notifyOnly"`，只写入，不唤醒

### 二、`session:send-custom` 这个 verb 把 `delivery` 吞掉了

verb 的 handler 只透传 `triggerTurn`：

```js
const h = {};
r?.triggerTurn !== void 0 && (h.triggerTurn = r.triggerTurn !== !1);
await s.deliverCustomMessage(c.sessionPath, d, h);   // 没有 delivery
```

所以经这条 verb 投递，**流式时固定走 followUp**，拿不到 `steer`。传 `delivery: "next-step"` 也没用。

要拿 `steer` 只能用宿主任务面（`ctx.tasks.create({ delivery: "next-step" })`），
但任务面在空闲时会起回合（唤醒），与「不打扰」冲突。

**当前取舍**：send-custom + `triggerTurn: false`，换来「空闲时不打扰」，
代价是「忙碌时消息排到回合结束才到」。这两个特性在现有两条路上只能各取一个，要同时满足需要宿主开口子。

### 三、投递目标必须给 sessionId，给路径会被拒

`session:send-custom` 的 `ro()` 把 payload 里的 `sessionPath` 包成 `{ legacySessionPath }`
交给 SessionManifestResolver，而那个 resolver 取路径只认 `e.sessionPath || e.path`（见 `_Pt`），
字段名对不上 → 抛 `Session manifest resolution requires sessionId or legacy sessionPath.`

所以投递只能给 `sessionId`。它不能从会话文件路径推导，必须在**工具 execute 期间**
用 `sdk.sessions.list({ scope: "all" })` 查出来、随任务存下去。

两个附带门槛：

- 不传 `scope: "all"` → 只列本 App 自己的会话，永远匹配不到用户的会话
- `scope: "all"` 需要能力 `app/sessions.read`（错误文案 "read sessions outside this app"），
  光有 `app/sessions.manage` 不够；能力变更要重装 App（install + confirm），reload 不认

### 四、实测时间线（2026-09-20，宿主 0.1013.2）

| 环节 | 实测 |
| --- | --- |
| 卡滞判定（阈值 30s） | 落盘 **31 秒** |
| 引擎 → App 扫描 → sendCustom 投递 | 1 秒内（App 扫描间隔 1 秒） |
| 写入会话（忙碌，followUp） | 本回合结束后 |
| 写入会话（空闲，notifyOnly） | 立即 |

引擎侧的停滞判定间隔原来等于阈值，第一次检查差一点永远不够，实际要等第二次 → 实测 60 秒才报。
改成「阈值/4 与 1 秒取小、下限 500ms」后降到 31 秒。

### 五、最终实现（当晚，按 APPS.md 修正）

用户指出投递说明文档要求一直是「拼进下一次 API 调用」（next-step）。查 APPS.md
「后台任务与审批（投递档位自 0.931.0 起）」确认：

- 正路是 `ctx.tasks.create({ callToken, label, delivery: "next-step" })`，令牌只在 execute 期间有效，
  之后后台只保存 taskId、结算时用 `complete/fail`
- 原文：next-step「不打断在途模型请求……正在运行（包括等待工具）的会话会在下一次输入收集点接收结果，
  空闲会话则启动后续回合。**App 不需要、也不应轮询 isStreaming**」
- 而 `session:send-custom` 在流式会话里固定 followUp（排到回合结束），实测延迟 29~189 秒

所以卡滞提醒改成：**execute 期间建一个 next-step 宿主任务**（与下载回执同一机制），
把 taskId 存进下载任务；卡滞时 App 用 `sdk.tasks.complete(stallTaskId, { text })` 结算。
下载终态时若该任务没用上，用 `cancel` 收掉（遗留的 pending app-task 会挡住短定时，见第 17 条）。

**重试通知仍是 `session:send-custom`**：重试由管理器 UI 发起，没有会话令牌，
`ctx.tasks.create` 在无令牌时 `scope` 只能是 `"app"`、`delivery` 必为 `"none"`，拿不到 next-step。
这是宿主投递档位的边界，不是可以绕过去的实现细节。

### 六、收尾方式：abort 是静默的（实测，文档没写）

「预建但没用上」的任务必须回收，否则遗留的 pending 会挡住短定时（第 17 条）。
但 App 侧 `sdk.tasks` 的 22 个成员里**没有 remove**（启动时打印过成员名）：

```
create, get, list, update, complete, fail, cancel, requestApproval, respondApproval,
watch, schedule, getSchedule, listSchedules, updateSchedule, pauseSchedule, resumeSchedule,
unschedule, retry, abort, recycle, getDelivery, registerHandler
```

宿主的 `task:remove` 只存在于给模型的工具目录里，而 App 的 bus 白名单不含任何 `task:*`，绕不过去。

四个终结方法里：

- `complete` / `fail` / `cancel` 都会向会话投递一条结果（cancel 投的正文就是 `canceled`）
- **`abort` 不投递**。2026-09-20 实测：正常下载跑完，日志 `stall-task aborted (unused)`，
  会话里只有那条正常的「下载完成」回执，没有多余噪音

文档没有写「abort 不投递」，这条是踩出来的。**App 侧要静默回收任务，用 abort。**

### 七、这轮折腾的归因（为什么绕了这么大圈）

链路本身没问题。宿主的两条通道都是成熟机制，各自语义清楚：

| 通道 | 语义 | 我们用的地方 | 表现 |
| --- | --- | --- | --- |
| `ctx.tasks` + `delivery: "next-step"` | 后台任务结果，下一次输入收集点送达 | 下载完成/失败回执 | 几十次投递零故障 |
| `session:send-custom` | 自定义消息；流式时 followUp、空闲时 notifyOnly | （曾经）卡滞提醒 | 语义与需求不符 |

**问题出在选型**：卡滞提醒我图"轻"，走了 `session:send-custom`，而它的语义不是「下一次调用」。
为了让那条错误的通道勉强能用，我在它上面连着打了三个补丁：补 sessionId（宿主 `ro()` 与
SessionManifestResolver 的字段名不一致）、补 `scope: "all"`、补 `app/sessions.read` 能力。
换回 `ctx.tasks` 之后一次就通，剩下的只是收尾方式（cancel → abort）。

**可以带走的判据**：宿主给了文档的通道就用文档里的。看起来更轻的旁路，代价通常藏在语义里，
不在接口难度上。

### 复核（2026-09-20，宿主 0.1013.2）

用户问「宿主能不能在前端隐藏投递成功的通知」，重查一遍。**结论未变，仍然不能**，三条例据换成当前版本的：

1. 投递呈现描述 `turn_input_presentation` 的结构是
   `{ kind: "pre_reply_interlude", inputKind, customType, taskId, status, resultType, result, reason, deliveryMode }`，
   **没有任何显示控制字段**；`ctx.tasks.create / complete` 的参数表里也没有。
2. 会话级任务的 delivery 只收 `next-step` / `next-turn`（传 `none` 被拒），
   `none` 只对不进会话的 `scope: "app"` 任务开放。
3. 前端 `desktop/dist-renderer` 下 239 个 js 里，interlude 走 `appendInterlude` / `appendLiveInterlude`
   **无条件写入时间线**，没有一处按状态或来源决定画不画。

唯一的办法仍是打宿主补丁（在当前版本的 `lit()` 生成 `variant: "deferred_result"` 那一段加过滤，
宿主自己已有「图片/视频生成的成功态不配提示」的先例），代价同上。

**决定：不打。** 为一条居中提示去动宿主，收益太小而升级覆盖与台账维护是长期成本。
另外提醒一句：呈现层与投递层解耦，不打补丁也不影响送达。

### 复核二（2026-10-13，宿主 1.1.0-beta）

用户再问「现在宿主能隐藏投递成功的前端通知了吗」。宿主当天从 0.1013.2 跳到 **1.1.0-beta**，按新版重查。

**结论：居中提示仍不能从 App 侧隐藏；但新增了一个管「底部任务 chip」的口子。**

1. **生成结构仍无显示控制字段。** `Wpt()` 造出的 `presentation` 只有
   `{ kind:"pre_reply_interlude", inputKind, customType, deliveryId?, taskId, status, resultType, result?, reason?, deliveryMode? }`
   ——依然没有任何一维能控制「画不画」。
2. **渲染端唯一的静默条件只认媒体生成。** bundle 里的过滤函数
   `ar(K)` = `status==="success" && resultType ∈ {image-generation, video-generation, audio-generation}` 才返回 true；
   命中它的 `rr()` 才 `return null`（不画）。这是宿主内置 `UniversalMediaManager` 给自己开的门——
   它注册 kind 时带 `wakeOnSuccess:false` → 生成 `deliveryIntent:"ui_only"` → 结算走 `_recordUiOnlyTask`（不投递、不起回合）。App 够不着。
3. **App 侧彻底够不着这条通道。** App 的 bus 请求白名单（`sdk/app-bus-contract.js`，69 个动词）里
   **没有任何 task / background / deliver / notif 类动词**，`background-task:register-kind` 不在其中；
   而 App 建会话级任务时，宿主在 `ctx.tasks.create` 里**写死** `deliveryIntent:"trigger_parent_turn"`（bundle 第 131558 行）。

**新增口子：底部任务 chip 可隐（Hana ≥ 0.1016.0）。**
`ctx.tasks.create({ chipVisibility: "hide" })` 隐藏该任务在会话底部 chip 里的默认显隐，省略为 `"show"`，用户偏好优先。
**但这管的是会话底部那条任务条，不是聊天流里的居中提示** —— 两者是不同东西，别混。

**决定（John 2026-10-13）：仍需隐藏的是居中提示（interlude），选择不动。**
① 不打宿主补丁（升级覆盖 + 台账维护的长期成本大于收益）；② 底部 chip 也不加 `chipVisibility:"hide"`。维持现状。
官方口子未开，留待后续版本再复核。

## 37. 卡片进终态就停轮询，管理器的「重试」把任务复活后卡片永远不跟（2026-09-21）

**现象**（用户实测反馈）：在下载管理器里点「重试」，任务确实重新跑起来了，但聊天流里那张卡片
仍显示「已取消 / 失败」，速度、进度都不动，必须刷新前端（重新挂载卡片）才恢复。同时 agent
也不知道重试已发起，仍当任务是失败态。卡片、管理器、agent 三方各说各话。

**排查**：三条线索各自独立，合起来才是全貌。

1. 卡片侧：`poll()` 里写着 `if (FINAL_STATES[t.state]) stop()`。任务一进终态就 `clearInterval`，
   之后再也不查。而引擎的 `retry(taskId)` 是**在同一个 taskId 上把任务复活**（重置 state 为
   pending、清 error/note/停滞痕迹），不是新建任务。卡片不知道这件事，也不会自己去问。
2. 通道侧：管理器和聊天流卡片各跑在**独立 iframe** 里，改状态的动作（重试/取消/删除）没有任何
   通道通知卡片。项目里其实早有 `BroadcastChannel("hana-dl-cards")`，但只用于卡片之间同步
   「展开全部」，管理器没接进来。
3. agent 侧：`/retry` 路由只在**重试跑完之后**才投结果（`notifyWhenRetryDone`），受理那一刻
   不投。agent 手上是这条任务的旧终态回执，于是它以为任务仍然失败。

**根因**：状态变化由管理器发起，但卡片的监听生命周期在终态就结束了，两者之间也没有通知通道。
一个人改了状态，另一个人既没被告知、又已经不再看。

**解法**（三处缺一不可）：

- `ui/card.js`：终态不再彻底停轮询，改排 **5 秒慢查**（`IDLE_MS`），只为等任务被复活；非终态
  保持 300ms（`FAST_MS`）。轮询节奏改由 `poll()` 自己结束时排（`schedule(ms)`），不再由启动处
  的 `setInterval` 统一接管。
- `ui/card.js` + `ui/manager.js`：把管理器接进已有的 `hana-dl-cards` 频道。管理器在每个改状态的
  动作后调 `notifyCards(taskId)`（重试 / 取消 / 删除 / 全部取消 / 清空记录；传 null 表示全体），
  卡片收到 `taskChanged` 立刻恢复快频并马上查一次。广播不通时还有 5 秒慢查兜底。
- `index.js`：`/retry` 受理后先投一条「重试已发起」给原会话（`notifyRetryStarted`），跑完的
  结果照旧再投一次。

**一条边界**：任务**真的不存在**（被删除）时仍然彻底停（`stop()`），不要每 5 秒去问一个不存在的
任务。这跟「终态」是两回事：终态要留着慢查等复活，任务没了就没得等了。

**验证**：直接对引擎跑了一遍——起一个限速任务（running，1.0MB/8MB）→ 取消（canceled）→ 等 6 秒
→ 调 `/retry` → 同一 taskId 回到 running（进度重新从 111KB 起）。引擎侧状态流转正确；卡片那半
属视觉确认，需在真实聊天流里看。

## 38. 卡片「撑满聊天流 + 变高 + 展开收起失效」三合一：那是加载期，不是坏了（2026-09-21）

**现象**（用户实测反馈）：下载卡片会突然变成跟随聊天流整条宽度、高度也涨开、展开收起点了没
反应；管理器里的卡片同样；过一会儿自己恢复。另一个会话（Qwen 部署）的卡片也一样。

**排查**：

1. 先怀疑尺寸被改坏：翻 git 只找到一次改卡片尺寸的提交（`d98980b`，09-17，`CARD_WIDTH` 450 → 400，
   `index.js` 里两处 `preferredWidthPx` 同步），之后碰 `ui/card.js` 的提交（`53580cf` 抽
   `shared/display.js`、`3d6009c` 改一行文案）都没动过尺寸。
2. 卡片的诊断记录（`app-card-activity/*.jsonl` 里 `name:"diag"`）显示 `w` 长期稳定在 `want-1`
   （400 → 399），只有宿主信封 `envW.max` 随窗口浮动（774 / 749 / 672 / 503 / 448…）。
   也就是说公式没坏：**实际宽度 = min(卡片想要, 宿主信封上限) - 1**。
3. 真线索在 `renderer.log`：出问题那几分钟成批出现
   `Uncaught (in promise) HanaPluginError: Plugin host request timed out: hana.track.`，
   而卡片诊断记录的写入**停在那一刻之前**。宿主侧插件请求通道当时是堵的。

**根因**：卡片是 iframe，**尺寸不归它自己定**。挂载后宿主先按默认宽度渲染（跟随聊天流、高度按
内容撑开），要等卡片脚本跑起来调 `hana.ui.resize({ width })` 上报、宿主采纳后才收窄。`poll` 前的
`bindTask()`（向引擎认领任务）若被拖慢，`render()` 就晚，折叠事件也还没绑上。整个过程就是
「撑满 + 变高 + 点不动」；通道缓过来、上报补上，自己就好了。

**解法**：不改代码，认现象。看到这个组合先别翻 git，先看是不是**卡片刚重载**、宿主通道是否在
超时。要缩短这段窗口只能减少卡片重载次数（每次重载都要重走一遍），属宿主侧机制。顺带记一笔：
`hana.track` 那句没接 `.catch()`，超时会以 `Uncaught (in promise)` 刷日志，是噪音（可选清理项，未做）。

**怎么区分「加载期」和「真坏了」**：加载期会**自己恢复**（几秒到几十秒），而且三件事同时出现
（宽、高、交互）；真坏了只会坏一件且不恢复。另可查 `app-card-activity` 里最新 diag 的时间戳，
如果停在某个时刻、卡片却还在，说明当时诊断通道不通。

**衍生结论**：这份环境上「起→停→起」的完整循环无法在不提权的前提下全量实测（内核停不掉 → 端口一直在 → 起分支总走 alreadyRunning）。

**可复用的验证手段：假梯子测试法**（2026-10-04 用它跑通了完整启停循环）：

1. 把 `node.exe` 复制一份、改名为 `node-fakeproxy.exe`（避免杀进程时误伤真实的 node 进程）；

## 42. 卡片按钮监听累加：一次点击弹出上百个资源管理器（2026-10-11，issue #2）

**现象**（外部报告）：完成态卡片点「打开文件夹」，explorer 窗口持续弹出，数量随卡片停留时间增长；实测可瞬间上百个 `explorer.exe`，机器几乎卡死。管理器页不受影响。

**根因**：`ui/card.js` 的 `render()` 末尾**无条件**重新绑定点击回调，而 `render` 是轮询驱动的：

1. `if (root.innerHTML !== html) root.innerHTML = html;` —— 终态 `done` 的 html 稳定不变（无速度/ETA/阶段文案），DOM **不重建**，旧按钮节点保留；
2. 但绑定语句 `on("dl-folder", () => reveal("select"))` 在 `if` **之外**，每轮都执行；
3. 传入的是**每轮新建的箭头函数**，`addEventListener` 只对同一函数引用去重、对新建函数不去重 → 同一按钮上监听器 **+1/轮**；
4. 终态后 `schedule(IDLE_MS=5000)` **只降频不停止**（为等「重试」复活任务而刻意保留）→ 每 5 秒一轮。

于是「卡片停留 N 秒 ≈ N/5 个监听」，点一次 → N/5 次 `reveal` → N/5 个 explorer 窗口。

**最小复现**（离线，无需宿主）：
```js
const button = { _ls: [], addEventListener(e,f){this._ls.push(f)}, click(){this._ls.forEach(f=>f())} };
function render(html){ if (root.innerHTML !== html) root.innerHTML = html;
  const on=(id,fn)=>{const el=getElementById(id); if(el) el.addEventListener("click",fn);};
  on("dl-folder", ()=>{ hits++; }); }        // 每轮新建箭头函数
for (let i=0;i<12;i++) render("done-card");  // 12 轮慢查
button.click();                               // fired = 12
```

**修法（两道防线，已实施）**：
1. **主修**：`render()` 内不再绑定；改为**模块级事件委托**——`root.addEventListener("click", ...)` 挂**唯一一个**监听，按 `e.target.closest("[id]")` 分发。root 不随 `innerHTML` 重建而消失，故监听数恒为 1。
   - 注意 `dl-copy` 原先捕获 render 局部变量 `filePath`，委托后改从 `currentTask.filePath` 取。
2. **兜底**：`engine/server.js` 的 `/reveal` 加 800ms 同路径去重（`lastReveal`），即便前端某条路径仍意外重复调用，也不会一次炸出上百进程。

**验证**：修复后 100 轮 render → root 监听数 = 1、点 3 次触发 3 次（修复前每轮 +1）。`node tests/run-tests.mjs` 8 套件全过。

**教训**：把「绑定事件」放在「可能重复执行」的函数里，且绑定的是新函数字面量，就是监听累加的经典配方。轮询驱动的 render 尤其危险——它的「DOM 没变就不重建」的优化，恰好让旧节点与旧监听一起存活。要么用委托，要么把绑定放进重建分支并用稳定函数引用。

## 43. 历史下载记录凭空消失：三处自动清理把管理器变成"只记得最近"（2026-10-12）

**现象**（John 报）：管理器里的下载记录会自动消失，只有人去主动清理才该清除；聊天流里"之前下载的卡片"展开收起按钮点了没反应。

**根因（实测）**：引擎对终态任务有**三重自动清理**，叠加起来等于悄悄抹掉用户的资产：

1. `dlcore.js` `restore()`：只恢复 **24 小时内**的终态任务（`if (age < 24*3600*1000)`）——启动时就把老记录挡在门外；
2. `dlcore.js` `_persist()`：`KEEP_FINAL = 100`，终态按完成时间倒序只留最近 100 条，超出的**从内存删除**并随写盘永久消失；
3. `dlcore.js` `_createTask()`：`MAX_TASKS = 64`，新建任务时若超限就删最老的终态记录。

**折叠按钮为什么"按不动"**：卡片 `poll()` 每轮问引擎 `/wait`；任务被上面三重清掉后返回 `not found`，卡片走 `renderFail()` + `stop()`，整张卡退化成一行错误文本，按钮自然失效。**这不是折叠代码的问题**——纯前端的 `toggleFold` 只在 `render()` 出来的 DOM 上工作，任务没了卡片就先死了。（对照：旧代码 `on("dl-fold", toggleFold)` 传的是稳定函数引用，`addEventListener` 本就去重，折叠从来没被 issue #2 的"监听累加"波及。）

**修法（已实施，John 定：记录是持久资产）**：
- `restore()`：终态任务**全量恢复**，不再有 24 小时窗口；
- `_persist()`：去掉 `KEEP_FINAL` 裁剪，全量写盘；
- `_createTask()`：去掉 `MAX_TASKS` 上限（并发由 `_maxConcurrent` + 队列治理，与记录条数无关）；
- 保留用户主动路径：管理器「清空记录 / 删除记录 / 删除记录及文件」照旧是唯一移除入口。

**验证（实测对照）**：造一份含「5天前 done + 3天前 failed」的 `tasks.json`：
- 旧版引擎（HEAD）→ `/list` 返回 `[]`（被丢弃）；
- 修复版引擎 → `/list` 返回 2 条（全部恢复）。
`node tests/run-tests.mjs` 8 套件全过。

**教训**：持久化数据上加"防无限增长"的自动清理，一定要先问"这是用户资产还是缓存"。任务记录是资产，删它必须由用户发起。三处独立的裁剪阈值各自看都合理，叠在一起就是"历史莫名其妙没了"，排查时容易只盯其中一处。

## 44. 设置菜单被截断：body 只有内容高，absolute 浮层被 overflow:hidden 裁掉；正解 fixed（2026-10-12）

**现象**（John 报）：下载管理器的设置菜单（右上角齿轮）被异常截断，只看得见前 3 项，后面的设置项既看不到也滚不到。

**根因（实测）**：`html, body { overflow: hidden }` 的裁剪边界是 **body 的矩形**；body `height: auto` 时它在布局上只有**内容高**（任务列表为空时约 150px），而 `position: absolute` 的设置菜单从齿轮下方展开约 360px，超出 body 的部分全被裁掉。

诊断数字（临时浮层读数，小卡形态）：`innerH=594`、`innerW=391`，但 `body.scrollHeight=401`、`#dl-root` 仅 `150`；菜单 `top=42 bottom=401`。**视口 594 装得下 401 的菜单，裁剪者是 body 的 150 而非视口。**

**走过的弯路**（血泪，以免复踩）：
1. 先给菜单加 `max-height: calc(100vh - 52px)` + `overflow-y:auto`——无效。`vh` 在 iframe 里 = 卡片高，反而把菜单压小。
2. 改 `position: fixed` 未遂——当时建立在错误前提上（见下），且卡片是 page 形态，被更大的问题掩盖。
3. 给 `html, body` 加 **`min-height: 100vh`**——**这是错的，且后果严重**：`vh` = 卡片视口高，它把 `body.scrollHeight` 抬到视口高，而本卡靠 `reportSize()` 上报 `body.scrollHeight` 决定高度 → 卡片被顶成**整页大卡**（John 当场纠正）。

**真问题先于菜单**：本期真正该先做的是**卡片形态**。SDK 文档（APPS.md 第 1274 行）定义 `realization`：`"card"`（画布上的一张卡，**缺省**）/ `"page"`（宿主为它开一页、放它一张卡**占满**）。本卡从建仓起写的就是 `"page"` → 打开即整页大卡。对照 SDK 改成 `"card"` 后，小卡形态恢复。**排查 App 卡形态，先查 manifest 的 `realization`，别在 CSS 里猜。**

**修法（已实施，最小改动）**：
- `manifest.json`：manager 卡 `realization` `"page"` → `"card"`（恢复小卡）。
- `ui/manager.css`：菜单 `position: absolute` → **`position: fixed`**。fixed 元素的包含块是**视口**，不受祖先 `overflow:hidden` 裁剪——正是同页行内下拉 `.mgr-row-menu` 用的办法（其注释早写着「避免被列表 overflow 裁剪」）。
- `ui/manager.js`：fixed 失去 `top`/`right` 静态锚点，新增 `placeSettingsMenu()` 按齿轮 `getBoundingClientRect()` 摆放并夹在视口内（下方放不下则向上展开）。

**验证（真机截图）**：小卡形态下点齿轮，菜单 10 项完整显示（当前 / 设置默认下载地址 / 助手选择下载地址 / 代理 / 代理启停 / 扫描代理软件 / 实测当前配置 / 停滞判定阈值 / 默认限速 / 同时下载上限），卡片仍旧是小卡。`node tests/run-tests.mjs` 8 套件全过。

**教训**：
1. **先查权威定义再动手**：App 卡形态（`realization` / `cardForm`）以 SDK 文档（`APPS.md`「卡片尺寸与形态契约」章）为准，不要凭手感改 CSS。本期两次大错（100vh 把卡顶成整页、起初误判为裁剪 bug）都源于跳过文档。
2. `overflow: hidden` 的裁剪边界是**该元素的矩形**，未必是视口；`body { height:auto }` 时它在布局上只有内容高，浮层贴着这条线被切。
3. **浮层逃出裁剪的首选是 `position: fixed`**（包含块是视口），不是撑高容器——后者在“高度靠内容上报”的卡上会引发高度环。
4. 怀疑被裁剪，第一步量诊断数字（innerH / body scrollHeight / 浮层 top-bottom），不要连续撤改 CSS。

## 45. 切会话回来卡片变满宽 + 变高：尺寸上报的去重键把宽度一起按住了（2026-10-13）

**现象**（John 报）：聊天流里的下载卡片，**切换会话再切回来**就变成满列宽、高度也涨开（像详情展开的高度）。
用户直觉：是卡片与宿主的通讯问题。

**先排除两件事**：
1. 开发目录与运行副本 `ui/card.js` 等 5 个文件 SHA256 完全一致 → 不是「改了没同步」。
2. 不是踩坑第 38 条那条「加载期三合一」——那条的前提是通道堵且**几秒到几十秒内自愈**；本例切回后不自愈。

**根因（读码所得，未做真机埋点复现）**：`ui/card.js` 的 `reportSize(force)` 去重键**只有高度**：
```js
if (!force && h === lastReportedH) return;   // 高度没变 → 整条 return
```
宽度是常量、不参与判断。于是**高度没变时连宽度也不发**。而一张进入终态的卡，内容高度恰好是稳定的——
它默认「没什么好报的」，一声不吭。宿主收不到宽度上报，卡壳就停在 CSS 的 `width:100%`（满列宽）；
高度同源：宿主未被上报时按默认/`aspectRatio` 推导，于是**满宽 + 高**一起出现。

**为什么切会话会触发**：聊天流按会话渲染，切换会话时当前会话的整棵聊天树卸载、切回时重建
（iframe 重新加载、脚本重跑）。重建后宿主手里的尺寸 state 归零，回到默认；卡片本该重跑后重报纠正，
但**能强制重报的窗口很窄**——脚本加载的约 9 秒（`bootSettle`）＋ 进入终态时的一轮（`terminalReported` 一次性）。
窗口过后只剩「按高度去重」的常规上报。若重建瞬间的上报落在窗口之外或未被采纳，就**永久停在默认尺寸**。

**关键订正：App 卡走哪条上报通道（纠正一条过期结论）**
- 下载器的卡是 `details.card` → `plugin_card` 块（会话记录里身份为 `cardInstanceId: a_...`、
  `cardEntityId: app-card:a_...`），渲染组件是 `VQ`（PluginStreamCard），**尺寸走 SDK 的 `ui.resize`**：
  卡片 `postMessage({kind:"event",type:"ui.resize",payload:{width,height}})` → renderer `xz()` 解析 →
  host hook `He(size)` → `Oz(slot="card")` 采纳（`Math.max(50,width)` / `Math.max(30,height)`）。
- `aQ`（InteractiveArtifactFrame，接顶层 `hana.card-resize`）是**另一类卡**（`show_card` 铸造/交互卡）的组件，
  不是下载器卡的真身；`hana.card-resize` 那条注入桥（server `_J()`）只服务 show_card 铸造/导出/卡库截图路径。
- ⇒ **踩坑第 10 条「宽度上报对 v2 应用卡不生效」已作废**（0.978.0 起生效）；本次读 1.1.0-beta 亦确认
  card slot 采纳上报 width。**旧结论不要当现状用。**

**修法（已实施，仅 `ui/card.js`，+43/−5）**：
1. **去重键纳入宽度采纳状态**：新增模块级 `widthProbeUntil`（探查窗截止时刻），非 force 时若
   「探查窗开着且 `|innerWidth - CARD_WIDTH| > 2`」则照发；宿主采纳或窗口过期后自动回到零开销。
2. **探查窗开启**：`bootSettle` 启动时（重建/重载时这段重跑，窗口自然重开）＋ re-show 处，各设 12s 上限。
3. **re-show 补报**（覆盖「隐藏再显示」路径）：监听 `visibilitychange` / `pageshow`，触发时开窗 +
   0/400/1500ms 三次一次性 `setTimeout` 强制补报。**纯事件、零轮询。**
4. **收兵判据加严**：`adopted()` 由「宽度达标就收兵」改为「宽度达标**且**本轮已真实发出 ≥2 次上报」，
   避免宽度恰好≈400 时误判已采纳、一收兵就再无纠正机会。
5. **探查期节流**：探查放行的上报加最小间隔 1s（活跃期 300ms 轮询否则会连发）；连续 re-show 以 400ms 合并。

**硬约束（John 明令）**：不要把 App 越修越重、避免不必要的轮询。故**零新增常驻定时器**
（`setInterval` 前后都是 4），`FAST_MS=300`/`IDLE_MS=5000` 未动，探查窗 12s 后自动归零。

**成色**：根因有代码依据（`return` 确在两条发送之前）但**未真机复现**；修法为静态推导。
测试 `node tests/run-tests.mjs` 8/8 套件通过（46/48/11/10/32/17/25/11）。

**部署与生效**：改 `ui/*` 同步运行副本即可，**不需要重启宿主**（静态资源按请求读文件）；
但已挂载的旧卡片不会变——要让它们也变需重开卡片或重启宿主。
因切会话本身会重建 iframe、重跑脚本，所以「切走再切回」就是一次天然的真机验证动作。

**教训**：
1. **去重/节流的键要包含所有「你希望被纠正的维度」。** 只按高度去重，等于把宽度这道门一起锁死；
   「省一次上报」与「错一整个尺寸」是同一笔账的两端。
2. **「卡片自己量的值」≠「宿主实际采纳的值」。** 只记前者的去重逻辑，永远发现不了外部已经变了——
   要有一个「宿主是否采纳」的对照，才能在对方重置后自愈。
3. **同一外观可能是两种生物**：App 卡（`plugin_card`→`VQ`→`ui.resize`）与 show_card 卡（`aQ`→`hana.card-resize`）
   是两条独立通道。排查前先从会话记录确认卡片身份（`cardEntityId` 前缀），别按外观猜组件。
4. 两路调研结论冲突时不要二选一采信：**自己下场从原始记录（会话 jsonl / bundle）取一次实测**再裁。

## 46. 聊天流内联卡整块消失：宿主 1.1.7 引入工具规范名，卡片的归属解析与验签双双失配（2026-10-15，宿主 1.1.7-beta）

**现象**（John 报）：聊天流里的下载进度卡**完全不见**，连块都没有（不是白屏、不是空卡，是整个 `plugin_card` 块不存在）。
时间线：宿主当天 20:38 从 1.1.0-beta 升到 1.1.7-beta；同一天 App 上了 P0 主题系统。两件事撞在一起，先辨因。

**先排除 App 与 P0**：
- 下载本身正常：产物落盘、管理器记录正常、引擎 `register-card OK`（卡片↔任务绑定成功）。
- P0 只动 `ui/`（卡内长什么样），决定不了「块出不出」；把运行副本 `ui/` 整回 P0 之前，故障依旧。
- 运行副本与开发仓 6 个关键文件 SHA256 逐一致，不是「改了没同步」。

**关键取证（都实测）**：
1. **卡片块不持久化**：会话 jsonl 的 `message.content` 里从来没有 `plugin_card` 块——它是投影期现算的。所以「`/api/sessions/messages` 里 plugin_card=0」**不能**作为「卡没生成」的证据（早期误判，记此以正）。
2. App 返回的 `details.card` 每帧完整（pluginId/route/cardInstanceId/aspectRatio/cardForm…），与 10-13 正常期逐字段同构。
3. **唯一变化的字段是 `details.bridgedTool.name`**：正常期是短名 `download-file`，今天变成规范长名 `app__hana-downloader__download-file_532f1d73a2c7`。
4. `hanaAppCardSource` 签名里解出的 `toolName` 仍是**短名** `download-file` → 与第 3 条的规范名**不一致**。
5. 判决性探针：把 `ui/card.html` 换成带 `console.log` 的探针页并 reload，发一笔下载，`renderer.log` 里探针日志 **0 命中** → iframe **根本没被创建**（排除「白屏/渲染空」）。

**根因（读宿主 bundle 1.1.7 vs 1.1.0 所得，逐处代码确证）**：
宿主投影链路 `SD → tOr → E_e/k_e`。`tOr` 只在两条分支补 `channel:"app"`：
- 分支 1：`hanaAppCardSource` 验签通过（`cPr`）。
- 分支 2：`resolveToolOwner(I_e)` 解析出唯一所有者且与 `details.card.pluginId` 相等。
- 分支 3（兜底）：**不补 `channel`**。

而 1.1.7 新增工具规范名机制：
- `Gvt(appId, localName)` = `app__<appId>__<localName>_<sha256[:N]>`；注册时给模型的是**规范名**（`name: Gvt(e, Se)`；1.1.0 无此行）。
- `zhe()` 在工具返回时**覆盖** `details.bridgedTool = { name: e.name（规范名）, server: ownerId }`。
- 而签名生成 `lPr → iPr` 传入的 `toolName` 是**本地名**（`Se`）；`toolNamesByPlugin` 登记的也是**本地名**（`recordRegistered(Se)`）。

于是投影时：
- `nOr(t, e)`：`t` 已是规范名（≠ `"tool_call"`），直接采用 → `SD` 拿规范名去解析。
- 验签 `cPr`：`proof.toolName（本地名） !== effectiveToolName（规范名）` → **invalid**（分支 1 失）。
- 归属 `I_e`：查 `toolNamesByPlugin`（登记本地名）里有没有规范名 → **找不到** → 返回 null（分支 2 失）。
- ⇒ 落分支 3，块**无 `channel`**。

客户端 `PluginStreamCard`（1.1.0 的 `VQ` / 1.1.7 的 `kte`，两版逻辑一致）：`v = e.channel === "app"`，`Rs(pluginId, route, v?"app":undefined)` 拼 URL：
- `channel:"app"` → `/api/apps/hana-downloader/ui/card.html`（实测 **200**）
- 否则 → `/api/plugins/hana-downloader/card.html`（实测 **404**）
⇒ 无 channel → 404 → iframe 不创建 → 卡完全不显示。

**这解释了「以前正常」**：1.1.0 没有规范名，`V.toolName` = 本地名 = 签名 toolName = owner 表登记名，三者一致 → 分支 2 成立 → 有 `channel:"app"` → 卡显示。

**影响面**：所有走 `details.card` 的 v2 App 在 1.1.7 上应同样受影响（不止下载器）。跨 App 抽样对照：仅 1.1.7 之后的记录出现「bridgedTool.name 长名 vs 签名短名」的失配，1.1.0 时期的记录（下载器 / comfyui-hana / hana-model-viewer）全部一致。

**性质**：宿主 1.1.7 内部不一致——签名写本地名、验签比规范名；owner 表登记本地名、查找用规范名。App 侧无从规避（规范名 hash 由宿主生成，`channel`/`bridgedTool` 都被宿主重写，App 填的会被剥离）。

**候选修法**：
- A. 宿主修复：把规范化打通（owner 表与签名统一用规范名，或验签/归属前把规范名回映射到本地名）。需报 issue / 等版本。
- B. App 侧自救：退回 `messageRenderers` 通道（`session:send-custom` + manifest 声明 `cards` 与 `messageRenderers`）。该通道的投影分支**无条件** `channel:"app"`，可绕开本题。代价：send-custom 在流式中会排成 followUp，投递不如工具返回值即时；卡片身份绑定要重做。
- C. 暂不处理，等宿主下一版。

**未决**：以上为代码级确证 + 探针间接确证，**未做「改宿主后卡恢复」的直接真机复现**（宿主不可改、不宜改）。

**教训**：
1. **两份 bundle 逐字节一致 ≠ 行为一致。** 差异可能不在代码，而在**输入数据的形态**——本例工具名从本地名变成规范名，投影/验签/归属三处全部踩空。对比版本时，除了 diff 代码，还要 diff「喂进代码的那份数据」。
2. **「字段存在」不等于「字段被采用」。** `bridgedTool.name` 一直在，但没人验证它换了值；`channel` 从来没在 `details.card` 里，却决定了 iframe 的生死。找故障要盯「下游真正读的那几个键」。
3. **探针比推理快。** 把目标页换成会打日志的最简页，一次 reload + 一笔下载，就排掉了「白屏/渲染空/资源 404」一整片猜测。
4. 版本升级与自家改动同日发生时，**先把「块出不出」与「块里画什么」分层**：前者在宿主投影链路，后者才轮到 App 的 `ui/`。分层对了，才不至于把力气花在错误的层。

## 47. 一类事故的五个面：契约失守、字段丢失、谎报成功（2026-10-18）

一次会话崩溃（`content[0].text = null` → 宿主读 `.length` 抛错）修完之后，按同一病理扫全仓，又挖出五处同源问题。合并记为一条，因为**病因是同一个**：*「形状不对的值」被当成了「正确的值」*。

**面 1：契约失守（callEngine 返回裸字符串）**
`JSON.parse` 失败时旧代码 `return text`，调用方按对象用 → `r.ok` / `r.taskId` 全是 `undefined`，于是「引擎回了个代理错误页」被显示成「任务已发起」。修法：解析失败返回 `{ok:false, error:"engine non-JSON: …"}`，形状恒为对象；所有调用点逐一确认对 `{ok:false}` 有分支（`/download` `/command` `/wait` `/cancel` `/retry` `/proxy-control` `/register-card` 与探活）。

**面 2：字段丢失（summarize 只留 14 个字段）**
`/list` 用 `tasks.map(summarize)`，而 summarize 是给 `finished/*.json` 写事件用的精简快照，**丢掉了 unit / stage / stageDetail / percent / speed / elapsed / queued / kind / startedAt / finishedAt**。后果全是显示层塌陷，且互不相同：git/pnpm 的对象数被当字节（`12 B`）、有 total 时百分比整段消失、耗时与起止时间恒空、速度不显示、winget/pip 的真实阶段看不到（恒显示兜底的「安装中」）。

根因不是「少写几个字段」，而是**同一条数据有两个摘要口径**（`/wait` 用 `snapshot()`，`/list` 用 `summarize`），UI 却用同一套代码消费两处——语义漂移必然发生。修法：摘要收成 `engine/summary.js` 的 `summarizeTask`，`percent` 按 `snapshot()` 的口径现算（`Math.min(100, received/total*100)` 再 round 一位），`/list` 与两处落盘共用一份；测试里用「管理器实际读的字段表」做断言。

**面 3：谎报成功（winget 退出码 null 被当成 0）**
`classifyWingetExit` 第一行 `Number(rawCode) >>> 0`。Node 的 `child.on("close")` 在子进程**被信号杀死时给的是 `null`**，而 `Number(null) >>> 0 === 0` → 命中 `case 0x00000000: return {state:"done"}`。于是一个 SIGKILL 掉的安装被记成「安装成功」，写进 tasks.json / finished/*.json / `/list` / 宿主回执。这是**用户会以为装好了**的那类错误，比显示错更严重。

同一入口的 `Number()` 还会把 `undefined` / `"abc"` / `{}` / `""` 一起变成 0。修法：先判类型（只接受 number 与数字字符串），再 `Number.isFinite`，最后才 `>>> 0` 保留大 HRESULT 码的归一能力。

**面 4：脏数据（undefined 字面量进模型可见文本）**
显示名用 `a || b || c` 拼，全空时 `undefined` 一路漏进 `下载 undefined`、宿主任务 label、卡片标题；卡片的 `stateBadge(s)` 在 `s` 缺失时把 `undefined` 原样返回，渲染成字面量徽标 + `class="b-undefined"`（样式全丢）；管理器的计数拼接在 `received` 缺失时出 `undefined/68 包`。修法：`displayNameOf()` 收口（永不为空）、`stateBadge` 落 unknown 桶、计数走 `?? 0`。

**面 5：「取消」的形状与消费方不符**
`/cancel` 返回 `{ok:true, result}`，而工具面读 `r?.snap`（拿不到 → 「半成品已保留供续传」永远不显示）与 `r?.ok !== false`（任务不存在时顶层仍是 true → 回「已取消」）。修法：同时给 `snap`（`mgr.snapshot()`，并顺带把 `partPath` 补进快照），顶层 `ok` 取与 `result.ok` 的合取。

**教训**：
1. **崩溃类事故修完要立刻做「同类形状」扫描。** null 进 `content[].text` 是一个点，`undefined` 进模型文本、`null` 当 0、裸字符串当对象是同一片面上的其它点。只补一个点，下一次换个入口再炸一遍。
2. **「有字段」与「字段被语义正确使用」是两件事。** 管理器读 `t.percent`、`t.unit`、`t.elapsed` 从来没报过错——因为 `undefined` 是合法的 JS 值，只是渲染成空白。这类静默丢字段比抛错更难发现，只能靠「字段表断言」兜。
3. **两个快照口径并存时，先合并口径再改 UI。** 否则会在 UI 里写出一堆 `?? 兜底`，把真正的语义漂移糊住。
4. **`Number()` 是宽松到危险的转换器。** `Number(null)`、`Number("")`、`Number([])` 全是 0。任何「0 有业务含义」（成功、无限、无限制）的地方，都必须先判类型再转换。

## 48. aria2 三条「看起来对、实际假」的数字（2026-10-18，W2）

接 aria2 做第二个 backend 时，逐条实测撞出来的三个坑。**共同点：数值有、格式对、来源假。**

**坑 1：`.part` 的文件大小不是进度。**
`file-allocation=none` 下 aria2 照样会把目标文件开到全长（默认它甚至预分配）。实测：一个 1.2MB 的文件刚开始下（`completedLength` 才 300KB），`.part` 已经是 1,198,576 字节。
如果拿 `statSync(.part).size` 当 `received`，界面立刻显示 99%，进度条整段是假的。
更阴的是它还会串到别处：`dlcore.restore()` 对中断任务用 `.part` 大小还原 `received`——这是 node-http 的正确做法（`write` 流是顺序追加的），但对 aria2 任务会让重启后进度直接显示 100%。
修法：进度只认 RPC 的 `completedLength`；`restore()` 对 `backend === "aria2"` 的任务跳过 `statSync` 兜底。

**坑 2：`status === "complete"` 不是「文件正确」。**
这跟上一轮续传 bug 是同一条教训的另一面：aria2 的 `complete` 只表示「我这边传输结束了」。
实测：给 `aria2.addUri` 传一个错误的 `checksum`，它下完之后 status 可能已经走到 `complete`，而我们如果照着 `complete → done` 映射，用户会拿到一个内容错误的文件，界面还写着完成。
修法：`complete` 在映射函数里保持叫 `"complete"`（`mapAria2Status` 单测里专门断言它 `!== "done"`），
交付判定集中在 `finalizeComplete()`：`completedLength === totalLength` + 文件大小 === `totalLength` + （有摘要时）流式 SHA-256 比对，全过才改名交付。

**坑 3：重试时残留的 `.aria2` 控制文件会让它「秒完成」。**
下载完成、`.part` 改名交付之后，那份 `.part.aria2` 还留在磁盘上（aria2 的名字是 `<out>.aria2`）。
下一次同名任务 `addUri` 时，aria2 读到控制文件，认为「这些段都下完了」，直接回 `complete`——而复用同一路径的新任务其实一个字节都没下。
修法：交付成功后连同 `<part>.aria2` 一起删；`errorCode=32`（自检失败）与 `8`（不支持续传）的失败分支也一并清掉半成品，避免下一次「立即完成 + 立即失败」的死循环。

**顺带一个必须记住的边界：`aria2.remove` 对已终态 gid 会报错。**
`Active Download not found for GID#…`。这不是失败，是「本来就没了」。取消流程要把它当「已 removed」处理，
否则会把一次正常取消记成「取消未确认」（又一个谎报的方向）。

**教训**：
1. **换传输引擎时，先问「这个数字是谁算的」。** 文件大小、状态字符串、进度字段在 node-http 里可以是一回事，在 aria2 里是三回事。同一个字段名（`received`）在不同 backend 下面必须是同一套语义，否则 UI 一定漂。
2. **状态映射要保守到「看起来没做完」。** 把 `complete` 映射成 `complete`（而不是 `done`）让代码别扭一秒，但把交付权留在有校验的那一层，能挡掉一整类「假成功」。
3. **控制文件是续传的前提，也是假完成的前提。** 交付成功即清、内容校验失败即清——留着它的唯一理由就是「下次还要续」，别的场景都是负担。

## 49. 把「没找到」也缓存 30 秒：用户装了 aria2 却必须重启引擎（2026-10-18，W3 验收）

**现象**：宿主引擎（已跑了一小时）调 `/aria2/status` 恒回 `reason:"未检测到 aria2c"`。
但同一台机器上：`resolveAria2Bin()` 手动调能返回 `C:\Users\...\WinGet\Links\aria2c.exe`，
另起一个新进程调 `capabilities()` 也回 `available:true, version:"1.37.0"`。
**同一个函数、同一份磁盘状态，老进程说没有、新进程说有。**

**根因**：`resolveAria2Bin()` 的探测缓存把「没找到」也当结果存了：

```js
binCache = { at: now, value: found };   // found 可能是 ""
if (binCache.value !== null && now - binCache.at < 30000) return binCache.value;
```

`value: ""` 不是 `null`，所以命中缓存分支、直接返回空。再叠上 `capabilities()` 的 5 秒探测缓存，
路径变成了：**用户在引擎运行期间安装 aria2 → 30 秒内怎么点都是「未检测到」→ 过了 30 秒还得
恰好错过 5 秒的 capabilities 缓存窗口 → 否则就一直看到旧结论**。实际表现就是「必须重启引擎」。

**修法**（一行）：

```js
if (found) binCache = { at: now, value: found };   // 只缓存成功
```

不缓存失败的代价是一次 `where.exe`（毫秒级），换来「装完立即可用」。

**边界**：用户**显式配置**的 `bin` 不存在时不走这个缓存分支（它本来就直接 `existsSync` 后返回空），
行为保持原样——那是「配错了」，应该稳定报错，也不能回落到 PATH（否则配置错误会被「碰巧找到的另一个
aria2」掩盖）。修完复核过：显式路径重复调用仍稳定返回空。

**教训**：
1. **缓存要区分「有值」与「没值」。** 用 `!== null` 判断命中是陷阱——"" / 0 / [] 都是「探到了结果」，
   但语义上「没找到」不是可缓存的知识，它是**环境的瞬时状态**（随时可能被用户改掉）。
2. **两个短缓存叠加，会放大成一个长的用户可见延迟。** 30s × 5s 的组合在这里等于「最多 35 秒不可自愈」，
   而且分布不均匀（要看两次请求落在窗口哪个位置），比单一 35 秒更难解释。
3. **「新进程好、老进程坏」是最强的定位信号。** 它把范围直接收窄到「进程内缓存」，不用怀疑磁盘、
   PATH、安装位置。看到这种分裂，先找模块级变量。
4. 验收这类改动时，**测试要能在旧代码上失败**。这次补的断言在临时回退化后确实红了 2 条
   （`放入后立即探测能找到 → ""`），才证明它抓的是这个 bug，而不是又一条「怎么写都绿」的测试。

> **2026-10-19 备注（本条修法已被取代）**：后来实测发现「完全不缓存失败」代价过高——
> `capabilities()` 是管理器每次打开都调的，一次完整握手 277ms，用户能感觉到。
> 现改为**分级 TTL**：成功 `DETECT_POSITIVE_TTL_MS = 10 分钟`，失败 `DETECT_NEGATIVE_TTL_MS = 5 秒`。
> 本条「只缓存成功」的结论不再是现行实现，但**教训仍然成立**：负结果不能被长期缓存，
> 只能是「宁可多试一次」的短窗口。实测缓存生效后第二次调用 8ms（对比首次 277ms）。

## 50. `.part` 的语义取决于谁在写它：换后端不能续用旧半成品（2026-10-19，F2-1）

**现象**：node-http 下了一半的任务，切到 aria2 继续，界面显示「完成」，实际交付的文件中间是空洞。

**根因**：同一个 `.part` 文件，两个后端写出来的**语义完全不同**。

| | node-http | aria2 |
|---|---|---|
| 写入方式 | 顺序追加 | 多段并行、各自 seek |
| `st_size` 含义 | 连续前缀长度，**可信** | 最远分片写到的偏移，**不可信** |
| 能否按大小续传 | 能 | 不能 |

`.part` 长度看起来是 D，但在 aria2 眼里只代表「最远的那个分片写到了 D」，D 之前的区域可能整段是空的。
于是 A 后端拿到的「已完成 D 字节」在 B 后端那里只是「最远触达 D」，续传就从洞中间接上，交付带洞文件。

**实测（32MB 随机源）**：取消时进度 9.0%，`.part` 已是 78.8%，洞占 **76.18%**、共 4 段，首洞在偏移 12,877,824。
重试后状态 `done`，**SHA-256 与源不符**，零值区与洞逐字节重合。

**修法**：不做洞检测，让 `.part` 跟后端绑定。

- 每个 backend 写入时打 `task.partOwner`（`node-http` / `aria2`），随任务持久化（`MGR_VER` 29）
- `_alignPartOwner()` 在续传前比对：归属 ≠ 本次 backend → 删 `.part` 与 `.part.aria2`、
  `received = 0`、`backendNote` 写「后端已切换（aria2 → node-http），旧半成品不可续用，重新下载」
- 修复后 A/B/C/D/E 五个用例 `match: true`

**为什么不做洞检测**：真零内容与空洞在磁盘上不可区分（合法文件本来就可能有大段 0x00）。
任何基于「扫零区」的判断都会误伤正常文件，或者放过真正的洞。**唯一可靠的信息是「谁写的」**，
那就把这条信息记下来。

**教训**：
1. **同一个字段名，换实现就换语义。** `received`、`size`、`length` 这种词看起来自明，
   但「长度」到底是「连续前缀」还是「最远触达」，取决于写它的人怎么分配偏移。跨后端复用前先问这一句。
2. **不可判定的状态，用溯源代替检测。** 与其猜「这个文件完不完整」，不如记「这个文件是谁写的」。
   前者需要理解内容，后者只需要一个字段。
3. **洞是静默的。** 带洞文件能通过大小校验、能通过状态校验、能在播放器里正常开始——
   只有完整算一遍 SHA 才现形。这类问题必须在交付路径上挡，不能靠用户发现。

## 51. 测试并行要同时隔离端口**和**临时目录，只改一个等于没改（2026-10-19）

**现象**：两份 `run-tests.mjs` 同时跑，随机失败：`EADDRINUSE`、`ENOENT rename`、SHA 对不上。

**三阶段实测**（每阶段都实跑，不是推断）：

| 阶段 | 改动 | 结果 |
|---|---|---|
| 原始 | 端口硬编码 18984-18998、临时目录固定 `%TEMP%\hd-dl-test` | 必撞 `EADDRINUSE` |
| 只改端口 | 全换 `listen(0)` | 仍挂，`ENOENT rename` |
| 两者都改 | 端口 + `fs.mkdtempSync` | 并行两份均 19/19（后为 20/20）、零 FAIL |

**根因**：端口冲突是**显性**的（起不来，立刻报错），临时目录冲突是**隐性**的——
两个进程都成功打开了同名文件，互相覆盖，直到某一步 `rename` 找不到源文件才炸，
或者更糟：SHA 静默对不上但没断言就过去了。

**教训**：
1. **显性冲突修完，别急着宣布「并行已支持」**。真正的隔离要覆盖所有共享资源，
   端口只是最容易被想到的那一个。临时目录、固定文件名、共享日志、单例锁，都要过一遍。
2. **隔离的验收标准是「同时跑两份都绿」，不是「代码里写了 `listen(0)`」。**
   第 2 阶段就是照着「写了 `listen(0)`」验收的，结果假绿。
3. 断言里带 SHA 的测试对并行极其敏感——`rename` 竞争会让两份进程拿到对方的中间态。
   这类测试要么彻底隔离，要么串行跑。

## 52. reload 会杀掉正在跑的子代理任务：顺序必须倒过来（2026-10-19）

**现象**：派出去两个修复任务，两分钟内先后报 `background task interrupted by process restart`，
工作区干净、文件一行没改。

**时间线**：

| 时刻 | 事件 |
|---|---|
| 02:53:40 | 同步脚本 reload，引擎重启 |
| 02:54:00 | 派任务 A |
| 02:54:33 | 派任务 B |
| 02:56:34 | 引擎**再次**重启 |
| 02:56:43 | 宿主主进程重启 |
| — | A、B 双双中断 |

**根因**：`reload` 不只是换渲染资源，它会重启 App 的 engine 进程（`apply()` 里先
`stopStaleRuntimes()` 再 `startEngine()`），而**进程重启会带走挂在这个宿主下的所有后台任务**。
reload 也不是一次性的：它会引发一串连锁重启，持续一到两分钟。

在连锁重启的窗口里派任务，等于把任务扔进还在震动的机器里。

**正确顺序**：

```
派任务 → 等全部完成 → 提交 → 同步 + reload → 验证
```

不是「同步 + reload → 派任务」。后者看似省时间（并行），实际是把任务扔进重启风暴。

**判断环境是否稳定**：看引擎进程 PID 是否连续 45 秒不变（`Get-NetTCPConnection -LocalPort 4317`
找 OwningProcess，再 `Get-Process -Id` 取 StartTime）。PID 稳定才算稳。

**教训**：
1. **任何「重启类」操作都是一个屏障，不能与执行任务并行。** 重启不是一瞬间的事，
   它有一段尾巴，尾巴里派出去的任务默认会被杀掉。
2. **操作顺序要按「破坏性从低到高」排**：只读检查 → 改代码 → 测试 → 提交 → 部署。
   部署永远是最后一个，因为它会重置前面的所有运行态。
3. 任务被杀后**先查工作区有没有半成品**（`git status`），再决定重派还是续做。
   这次两个任务都没来得及动文件，重派成本为零——但那是运气，不是常态。

## 53. 两个小工具坑：数行数会少算，查进程会查不到（2026-10-19）

**坑 1：`Measure-Object -Line` 不统计空行。**

```powershell
(Get-Content file.md | Measure-Object -Line).Lines   # 1270
(Get-Content file.md).Count                          # 更多
```

`-Line` 只数**非空行**。报告「文件多少行」时用它，会得到偏小的数字；
而像「232 行砍到 141 行」这种对比，如果两次都用同一个偏小的口径，比例还算对得上，
但绝对值是假的。要真行数用 `.Count` 或 `Measure-Object` 不带 `-Line`。

**坑 2：引擎不在 `node` 进程里，`Get-Process node` 查不到。**

引擎跑在 `hana-win-sandbox.exe` 沙箱里，进程名是 `hana-server`。
`Get-Process node` 返回空，会让人误以为「引擎没起来」。
正确查法：

```powershell
$c = Get-NetTCPConnection -LocalPort 4317 -State Listen
Get-Process -Id $c.OwningProcess    # -> hana-server
```

**顺带记住沙箱的环境变量重定向**：`LOCALAPPDATA` 与 `USERPROFILE` 都被重写到
`<app-data>\.runtime-tmp`，但 `HOMEDRIVE` + `HOMEPATH` 没有被改。
要在引擎里定位真实用户目录，只能用后者。

**教训**：
1. **统计口径不明的数字不要写进报告。** 要么确认口径，要么两个口径都给。
2. **「查不到」和「不存在」是两件事。** 查进程先确认「它应该以什么名字出现」，
   而不是拿最常见的名字试一次就下结论。

## 54. `detached: true` 是双刃：能杀整棵树，也会在引擎被杀时留孤儿

**现象**：给 posix 的命令型子进程加 `detached` 之后，「取消」能杀掉 git/uv 拉起的孙进程了。
但引擎自己被 SIGKILL 时（宿主强退、任务管理器结束进程），这些子进程**不会跟着死**——
它们成了真正的孤儿，继续在后台写同一个目录，而 App 侧已经把任务标成「已中断」。

**为什么是同一个机制的必然代价**：`detached` 让子进程自成进程组（pgid = pid），
`kill(-pid)` 才有「组」可杀。代价就是它脱离了父进程的生命周期——这两件事是同一枚硬币。

**修法（两步）**：

1. `_persist()` 落盘 `childPid`（仅 `kind=command && state=running`，终态自动清空）
2. `restore()` 时 `_reapOrphanCommand(pid, cmdType)`：先 `pidAlive` 探活 → 再 `processNameOf` 核名 → 都对上才 `killTree`

**核名这一步不能省**：引擎停机一小时后，那个 pid 可能已经属于用户的别的程序。
只凭 pid 杀就是拿用户的系统赌运气。**拿不到进程名时宁可不动**——误杀代价远大于漏杀。

**成色**：三段原语（`pidAlive` / `processNameOf` / `killTree`）各自实测通过；
「引擎被 SIGKILL 后 restore 真的收掉」需要真机造现场，未实测。

## 55. 断言别押注「机器干净」，押注契约

**现象**：`unit-platform.mjs` 里有三条断言在 CI 上红、在本机绿：

```
FAIL: darwin.which("node") 在 Windows 上 → ""（本机无 which 命令，不抛）
FAIL: linux.which("node") 在 Windows 上 → ""（本机无 which 命令，不抛）
FAIL: win32.readSystemProxy: 启停两态自洽
```

前两条：`windows-latest` runner 上 Git for Windows 把 `which` 放进了 PATH，
于是 `darwin.which("node")` 真能拿到结果——**断言写的是环境，不是契约**。

第三条不是环境问题，是真缺陷（见 56）。

**改法**：押注契约——「不抛、返回字符串、要么空要么指向真实存在的路径」。
这个版本在本机和 CI 上都成立，验的仍是那件重要的事。

**教训**：写「某平台一定没有 X」这类断言前，先问「CI runner 上会不会有」。
唯一稳的写法是断言**行为契约**（不抛 / 形状 / 一致性），不是断言**环境事实**。

## 56. `readSystemProxy` 两态自洽（附：审查纠正了这条的重心）

**现象**：中间提交（`785e864`）里 `win32.readSystemProxy` 在 `ProxyEnable=1` 但 `ProxyServer` 为空时，
返回 `{enabled:false, server:"", source:"registry"}`。

**为什么是缺陷**：调用方必须在两个字段之间做判断——看 `enabled` 就是「没代理」，
看 `source` 就是「从注册表读到了」。这不是「两种都合理」，是自相矛盾。
`fb41084` 起改成 `if (!enabled || !server) return none;`。

**修法**：`ProxyEnable=1` 且 `ProxyServer` 非空，才算 `registry`；否则一律 `none`。

## 57. `spawnOpts` 只给 `spawn`，不要套到 `spawnSync` 上

**踩到的写法**：

```js
// 错：spawnSync 没有「脱离」这件事
const r = spawnSync("curl", args, platform.spawnOpts({ timeout }));
```

`spawnSync` 接受 `detached` 参数，但语义完全不同（同步调用不存在「脱离」），
可能影响子进程的会话归属，还让「这里到底要不要 detached」变成说不清的事。

**正确做法**：`spawnSync` 处只按平台决定 `windowsHide`：

```js
const r = spawnSync("curl", args, { windowsHide: platform.name === "win32", timeout });
```

**这是有意的不对称，不是漏改。** 在 `unit-processtree.mjs` 里没有断言拦它——
这属于「知道为什么这么写」的范畴，写进踩坑记录比写死断言更合适。

## 58. 「我以为的旧代码」不是旧代码：审查推翻了一条写错的教训

**这条本身是一次失败记录，留着当警示。**

原来这里写着：「`findPnpmEntry` 在 posix 上一直等于没写 —— 原实现只认 `.cmd`，
`which pnpm` 拿到 shebang 脚本恒不匹配，返回 null。新实现补了三段。」

2026-10-20 独立审查把 `f7de1b9` 的原函数翻出来逐行看，发现前提不成立：

```
1276:  if (!p || !/\.cmd$/i.test(p)) continue;     ← 第一段：只认 .cmd（确有）
1286:  // 2) npm root -g 直拼标准结构               ← 第二段：平台无关，被我漏看了
1288:  const r = spawnSync("npm", ["root", "-g"], ...)
1291:  for (const f of ["pnpm/bin/pnpm.mjs", "pnpm/bin/pnpm.cjs"])
```

第二段与平台无关，`npm root -g` 在 posix 上正常返回 `/usr/local/lib/node_modules`，
`path.join` 拼出来就是对的。**posix 上只要有 npm 全局装的 pnpm，旧实现返回的是真路径。**
返回 null 只发生在 pnpm 不装在 npm 全局根下（standalone / corepack），
而那时退化路径 `spawn("pnpm")` 在 posix 上执行带 shebang 的 shim 本来就成功。

三条结论：

1. 「恒返回 null」「靠碰运气」都不成立。我新加的第三段，就是旧代码的第二段（几乎逐字）。
2. 我新加的那段 shim 正则（抓 `/../pnpm/bin/pnpm.cjs`）**是死代码**：
   `` 是 shell 变量，正则把它当字面目录名，`path.resolve` 后永远 `existsSync: false`。
   实测四个变体全部解析不出存在的路径。
3. 顺带一处**真退化**：`which` 只返回首行，旧代码遍历 `where` 的全部结果。
   本机 `where.exe pnpm` 返回两条（sh 脚本在前、`.cmd` 在后），这次靠第一条恰好可用蒙对；
   若第一条是残留的坏 shim、第二条才是好的，旧代码会跳过坏的，新代码不会。

**真正的教训（两条，比原版值钱）**：

- **写「旧代码是什么样」之前，必须把那一段完整读出来，不是凭 grep 一个片段下判断。**
  我当时搜到 `/.cmd$/` 就认定「只认 .cmd」，没看到下面还有一段兜底。
  凭片段推断旧行为，比不推断更危险——它会生成一条看起来很确凿的错误结论。
- **一条错误的教训比没有教训更难拆。** 它挂在踩坑记录里，后人会照着它去怀疑别处的
  `.cmd` 过滤是不是也有问题。删掉它比留下一句「这里可能有问题」代价更大。

**现在这套代码怎么处理**：新加的第二段正则保留（`existsSync` 兜着，无害），
但**不要以为它在干活**；真正救场的仍是 `npm root -g`。
`which` 只看首行这个退化记在这里，后续要修再修。

## 62. 「探活组长、杀进程组」：两层对象被当成了一个

这是**审查已经指出、这次在真机上数出来**的一条。写下来是因为它的形态很典型：
两个都「对」的函数被组合起来，结果在特定时序下什么都不做，而且**不报错**。

```js
// 旧写法（dlcore.js 的 _reapOrphanCommand）
if (!platform.pidAlive(n)) return false;   // 探的是「组长」
...
platform.killTree(n);                      // 杀的是「进程组」kill(-n)
```

`spawnOpts` 给了 `detached:true`，子进程自成进程组。于是有两种时序：

| 时序 | pidAlive(组长) | kill(-pid) 有东西可杀？ | 实际结果 |
|---|---|---|---|
| 组长还活着 | true | 是 | 正常 |
| **组长已死、组员还在** | **false** | **是** | **直接 return，什么也没杀** |

第二行就是这次造出来的现场（`tests/tools/orphan-posix-mechanism.mjs`）：

```
组长已退出（pidAlive=false）           pid=6749
组长死后组员还活着（心跳 14 -> 20）
★ 但进程树仍可探活（treeAlive=true）   -6749
treeNames 能问到组员                   ["node"]
```

**同一时刻、同一个 pid：一个说死、一个说活。** 不是某个函数写错了，
是**探活和操作的对象不是同一个**。这类错配的特点是：代码读起来天衣无缝，
只有造出那个特定时序才暴露。

**修法**：补 `treeAlive` / `treeNames` 两个平台接口，让探与杀指向同一个对象。

**一个必须一起验的前提**：组长已死时 `kill(-pid)` 会不会打到别人的组？
取决于进程组存活期间 pgid 是否可复用。`tests/tools/pid-reuse-vs-group.mjs` 实测
（300 次分配、300 个不同 pid）：

```
oldPid=4012 未被复用；组在此期间始终活着；组员仍在跑
```

**结论**：进程组存活期间 pgid 被内核占住，`kill(-pid)` 只指向我们当初建的那个组，可以安全清组。
不验这一条就杀，是拿用户的系统赌运气。

**通用教训**：当一个操作是「先检查 A 再对 B 动手」时，**要问 A 和 B 是不是同一个东西**。
不是同一个，就迟早有一条路径从中间漏过去，而且它不会报错。

## 63. 一次修复引入比原缺陷更危险的新缺陷：把 shell 当成合法身份

**这是我自己在修 #62 时闯的祸，比原缺陷严重，所以单列一条。**

修 #62 时，我把 `"sh" / "bash"` 加进了 `_reapOrphanCommand` 的期望镜像名，
理由写得很像回事：「真正的写入者是孙子进程，组长可能是个 sh 包装」。

**两半全错。**

**动机不成立**：四条链路全是直接 spawn（`git` / `node` / `winget` / `python|uv`），
全仓 `shell: true` 零处。真实树里 sh 只是中间层（`git → sh → git-upload-pack`），不是组长。
而 `sh -c "单个命令"` 会被 **exec 掉**，连作为独立成员都不存在 ——
我造验收现场时就撞到了：`bash -c "sleep 60"` 的树里只有 `sleep`，没有 `bash`。

**风险已经复现**：shell 恰恰是桌面上最常见的**组长**——终端里的每条作业、
每个 `setsid` 启动的服务、每个 login shell，pgid 都等于自己的 pid。

```
无关 bash 组长 pid = 24214
treeNames = ["bash","sleep"]
_reapOrphanCommand(24214, "pnpm-install") = true
0.7s 后 bash 组长还活着?  false      ← 整个组被打掉
```

纯 sh 组配 `pip-install` 同理。安全阀从「树里必须有真正干活的镜像名」
降级成了「树里有个 shell」。配上 pid 复用就是一次真实误杀
（复核用 `/proc/sys/kernel/ns_last_pid` 精确复现了）。

**更值得记的是我当时的推理链也有个洞**：我用「组存活期间 pgid 不可复用」
来支撑「kill(-pid) 安全」。这条**验了也是对的**，但它管的是「组还在」的情形；
而误杀恰恰发生在「组已经消失、pid 被复用」之后，那时新组完全陌生。
两件事被当成了一件。一条正确的证据被用在了它不管的结论上，这类错比证据错更难发现。

**修法**：
1. shell 全部移出期望集合（连 `dash` / `zsh` 也不列）。名字硬编码两头都不稳，宁漏勿错。
2. 加 `processStartOf(pid)` 启动指纹，把核名从唯一依据降为旁证：linux 读
   `/proc/<pid>/stat` 第 22 字段、darwin 用 `ps -o lstart=`、win32 有意返回 `""`。
   两边都有值且对不上 → 认定 pid 被复用 → 放弃。

**指纹也有它挡不住的**：jiffies 单位常见 100Hz（10ms），同一轮 fork 的进程落在同一个 tick、
指纹相同。它能挡「几分钟前的 pid 被顶替」，挡不住「10ms 内撞上」。写代码时不要以为它是万能的。

**一条可移植的教训**：**安全阀的每一项都必须能单独成立，不能靠「别的环节会兑住」**。
我加 shell 时的潜在假设是「反正还有名字核着」，但那个名字集合本身就不全——
两个不完整的阀叠加，不是更安全，而是彼此掩盖了漏洞。

## 64. 「源码正则断言」是装饰，不是防线

复核直接把我上一版 `unit-orphan-reap.mjs` 的 6 条「源码契约」断言拆了：

```
【现状】                            6 passed, 0 failed
【仅把 restore() { 重排成 restore(){】  2 passed, 4 failed
```

切片标记一失配，`body` 就是空串，而「这段文本里没有某个字符串」对空串永远成立。
两条带 ★ 的「防回归主力」永远不会因为代码退回错误口径而失败，只会在切片失配时静默通过。

**改法**：
1. 源码断言只留一条，并且**先断言切片本身有效**（`body.length > 200`），
   否则下面那句又变成空串上的无条件通过。
2. 其余全部换成行为断言：真起进程、真数心跳、真看谁死了。
3. 用**变异测试**验收这套件本身：把缺陷逐个放回去，看它是不是真的红。

```
变异 1（treeKill → killTree）        1 failed
变异 2（treeAlive → pidAlive）       3 failed
变异 3（sh/bash 加回期望集合）        3 failed
还原                                83 passed, 0 failed
```

**教训**：验证「测试有没有牙」只能用变异——把一个已知缺陷放进去，看它是否红。
跑绿不能证明任何事，因为不知道自己失败的可能性。这个项目早在审查 B 那次就学过一遍
（「我的测试验证的是我写了这段代码，不是这个功能在用户机器上对」），这次又踩了同一个坑，
只是形式不同。

## 65. `sh -c` 单命令会被 exec 掉，造现场时 "shell 不在树里" 是正常现象
**现象**：想造「一个 bash 组」的现场，用 `bash -c "sleep 60"` 起，结果
`treeNames` 只给 `["sleep"]`，没有 `bash`。当时以为实现错了。

**真相**：单个命令时 shell 会 **exec** 掉自己（不 fork），进程被替换成目标程序，
`comm` 变成 `sleep`，bash 作为独立成员根本不存在。这是 POSIX shell 的标准优化。

**要多命令才会留下 shell**：`bash -c "sleep 120; echo done"` 才是
`["bash","sleep"]`（`;` 之后还有一条要执行，shell 不能 exec）。

**为什么这个细节值得单列**：它会让你把「正确的行为」当成 bug 去修，
也会让你写出「恰好在单命令时通过、多命令时失败」的假测试。
造进程相关现场时，先想清楚 shell 会不会被 exec。

   这次就是靠补一条 `_persist → 读 JSON → restore()` 的端到端断言，才抽到两个真 bug
   （`t.child._childStart` 读错位置、`_resetTaskManager` 没清 globalThis）。
3. 藏在闭包里的判据要抽成具名函数。`escalationAllowed` 原本是 `scheduleEscalation` 里的
   一个内联闭包，自然条件下 pid 复用几乎不可能触发，所以“指纹变了就不升级”这条
   永远测不到。抽出来之后三种情形都能钉死。
4. **分层：行为归行为测，复用归静态测。** M7 变异的是「`treeKill` 还有没有调用
   `escalationAllowed`」，而单元测直接测的是 `escalationAllowed` 本身 —— 前者把调用
   内联掉，后者照样绿。需要一条“必须复用”的静态断言才能抓住。
   所以“源码正则都是装饰”这个结论有适用范围：判断标准是「这个断言能不能在缺陷回来时
   真的失败」，而不是“行为断言一定比静态断言好”。

**一句话**：从“测我写的代码”到“测它会不会错”，中间差的不是工量，是立场。

## 67. 注释里的反例会被静态断言当成真代码

静态断言（“源码里不得出现 X”这类）有一个很难绕开的边界：**它分不开注释与代码**。

2026-10-21 加 `unit-orphan-reap.mjs` 的静态契约时，想顺手禁掉 `process.kill(n, 0)`
这个字符串（它是升级探活退化的标志）。结果**假红**：

```
// treeKill 的注释里就写着：
// “升级探活要比对启动指纹，不能只看 process.kill(n,0) —— 复核发现…”
```

那段注释本身是对的（后人能看懂为什么要这么写），代价是纯文本断言会把它当成违规代码。

**解法不是删注释**，是换断言口径：不否定“出现了这个字符串”，而是肯定“必须调用 `escalationAllowed`”。
后者同样能抓到内联退化（M7 就是靠它抓的），而且不会被注释干扰。

**一般原则**：静态断言尽量写**肯定形式**（“必须调用 X”）而不是**否定形式**
（“不得出现 Y”）。否定式容易栽到注释、文档字符串、错误提示文案上。

## 68. 改完没提交就交给复核：两个人验的不是同一份代码

**现象**：2026-10-21 第三轮复核，我在派单前改了几处代码（`escalationAllowed` 从两参改三参、
retry 里补 `_childStart = null`），但没提交就发出去了。复核的结论开头就是：

> 工作区和 cf32f31 不是同一份代码。这轮四条结论里，第一条要加限定，
> 第三条的“8 个变异”在仓库里已经复现不出来了。

它读到 04:24 的版本（两参），到 04:30 再读到三参版本。同一个函数在两个版本里
**语义相反**（提交版“没指纹就保守升级”，工作区版“比名字，名字也没有就不升级”）。

更硬的后果：`mutation-check.sh` 里 M7/M8 的替换目标还是旧签名写死的字符串，
对工作区跑出 6/8、exit 1。也就是说「8 个变异全部被抓到」这句话对提交版成立、
对我要交付的代码不成立。

**根因两条**：
1. **派单前没同步代码状态。** 我把“改了”当成“交出去了”，复核拿到的是一份中间态。
2. **变异脚本脆性**：替换目标写死字符串，源码一改就失配；而脚本没有 `set -e`，
   python 的 `assert` 失败被后面逻辑当成“这个变异没被抓到”，报出的原因完全是错的
   （说套件没牙，其实是脚本没改成功）。

**做法上的改变**：
- 派复核前先 `git status` / `git commit`，让“我验的”和“你要交的”是同一份。
  这不是仪式，是让复核结论能落到具体 sha 上。
- 变异脚本每个变异后加一道 `if [ $? -ne 0 ]; then ... exit 2; fi`——
  “变异没应用成功”必须与“套件没牙”分开报，否则后人会去查错方向。
- 派单时把 sha 写进任务书，复核回话时也报 sha。

**为什么这条比代码缺陷值得单列**：代码错了还能靠测试抓，**两边验的不是同一份代码，
所有结论都没有落点**。这一轮的“3 个真 bug 全修好”差点变成一句空话。
