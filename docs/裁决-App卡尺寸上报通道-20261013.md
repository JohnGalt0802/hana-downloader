# 裁决：App 卡（hana-downloader）尺寸上报走哪条通道

> 日期：2026-10-13 深夜
> 背景：两枚举证得出**冲突结论**，本文件给出裁决与依据。宿主版本 1.1.0-beta。

---

## 一、冲突

| 来源 | 说法 |
|---|---|
| 首轮宿主侧调研 | 聊天流卡片接的是**顶层 `hana.card-resize`**（组件 `aQ` / InteractiveArtifactFrame）；`hana.ui.resize`（SDK）在聊天流「未找到接收方」 |
| 第二轮契约复核 | App 卡走 **`VQ`（PluginStreamCard）→ `rE()` host hook → `Wz/He/Oz`**，尺寸逻辑在 `app-host-view` chunk（`Math.max(50/30)` clamp，未抽出） |

两者指向**不同的组件、不同的通道**，必须分清。

## 二、裁决：App 卡走 `VQ` → `ui.resize`（SDK 通道）

**结论**：hana-downloader 的卡片是「工具返回值 `details.card` → `plugin_card` 块」，渲染组件是
**`VQ`（PluginStreamCard）**，不是 `aQ`。它经 `rE()` 挂载 host hook（slot=`card`），尺寸上报走
**`ui.resize`** 事件 → renderer `xz()` 解析 → `Wz` 内 `He(size)` → `Oz()` 采纳。
**首轮把 `aQ` 当成 App 卡的真身，属误判；`aQ` 是另一类卡（`show_card` 铸造/交互卡）的组件。**

### 证据（本机实测抽取）

1. **`plugin_card` 块 → `VQ`**：renderer `KQ({block})` → `i=e.card; UQ(i.type)` → `VQ({card:i,...})`；
   `VQ` 返回 `kind:"plugin-stream-card"`（`ChatTranscript-CLxbpBJm.js`，PluginStreamCard 组件段）。
   `Ea`（`statusLabel:"Chalkboard"`, `disabled:!0`）只是**未安装时的降级占位**，不是真身。
2. **`ui.resize` 解析器确实存在且在 App 卡路径**：
   ```
   function xz(e){ ... if(e.type===et.UI_RESIZE && _o(e.payload)){
     const r=Yc(e.payload.width), s=Yc(e.payload.height);
     return r===void 0&&s===void 0 ? null : {kind:"resize", size:{width:r,height:s}} } }
   ```
   消费点：`if(gt.kind==="resize" && s!=="input-panel" && He(gt.size), ...)`（`s`=slot，App 卡为 `card`，通过）。
3. **card slot 采纳 width/height**：
   ```
   const Iz=50, wz=30, QA=100, bz=48;
   function Oz(e,t,n,r){ if(e==="card"){ const i=t.width!==void 0?Math.max(Iz,t.width):n.width,
     a=t.height!==void 0?Math.max(wz,t.height):n.height; return {width:i,height:a} } ... }
   ```
   → 卡槽下**上报的 width 与 height 都被采纳**（下限 50/30）。
4. **`_J()`（注入 `hana.card-resize` 的 resize-bridge）的调用点全部是 `show_card` 铸造/导出/卡库截图路径**
   （`/api/cards/:cardId/t/:ticket/`、mint、library、screenshot），**不经 App 卡的 `/api/apps/<id>/ui/...`**。
   ⇒ 那条 legacy `hana.card-resize` 桥**不注入 App 卡**；App 卡里能生效的是 SDK 的 `ui.resize`。

## 三、对本次修复的意义

- `ui/card.js` 现行两条上报里，**`hana.ui.resize({width,height})` 是 App 卡真正生效的那条**；
  `postMessage({type:"hana.card-resize"})` 对 App 卡**不起作用**（无害，历史兜底，暂留）。
- 因此本次修法（探查窗 + re-show 补报 + 宽度纳入去重）**方向正确**：它驱动的正是 `ui.resize` 上报，
  且 `Oz` 确认 card slot 会采纳 width，所以「宽度纳入」不是白做。
- **附带发现**：App 卡路径上未发现「未 ready 就丢弃上报」的守卫（只有 `slot!=="input-panel"`），
  所以问题更可能出在**上报未被发出**（App 侧窗口关闭/时序），与本次修复假设一致。

## 四、仍未完全抽出的一处（不影响本轮结论）

`app-host-view` chunk 内 `rE`/`Oz` 的完整实现（含是否有额外守卫）因单行长压缩 + 只读工具限制未抽全；
但 `Math.max(50/30)` 与 `Oz` 的 card 分支已在 `ChatTranscript` chunk 内实测到（上面第 3 条），
数值与行为一致，足以支撑裁决。
